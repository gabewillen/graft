# RFC: Agent Grafts

Status: draft. v1 (depth 1, with parallel background grafts) is implemented in this repository; decisions below are fixed for v1 unless listed in [Open Questions](#open-questions).

## Summary

Agent Grafts is an architecture for isolating specialized work without giving up the flexibility of a single general-purpose agent, and without the information loss of agent-to-agent communication.

> **An agent is a timeline. Cloning suspends it; joining resumes it with the clone's timeline available as its own memory. Context is isolated on the way down and lossless on the way up.**

The name comes from horticulture: a cutting is taken from a plant and later grafted back so both grow as one organism. Here an agent clones itself into a single-use timeline, and that timeline is grafted back onto its source as memory.

The core principle is:

> **Replicate the agent, not its context.**

The user talks to one agent. When specialized work is needed, the agent **clones** itself into a new timeline that starts from the messages it points at (by pointer, like a git branch) and its own clone call, which carries, in its own words, what that clone is for; the clone holds only the skills it chose for it. The clone talks to the user directly, for one turn. When that turn ends, it **joins**: the source resumes with the conversation the user had with the clone, and the clone's last turn with its merge call, appended to its own memory, by pointer, with no model call, and runs once.

Several clones can exist at once, but **at most one branch holds the conversation**. One clone call creates one or more clones: at most one is the **focus** graft, which takes the conversation as described above, and the rest are **background** grafts, which work concurrently, never talk to the user, and join back when they are done while the source keeps the conversation (see [Parallel grafts](#parallel-grafts)).

The problem this solves is *lost in translation*: no worker ever summarizes its own work for someone else. What comes back is the record itself: the conversation the user actually had with the clone, joined by pointer.

## Terminology

| Term | Meaning |
|---|---|
| **original** | The user-facing agent at the top of the chain. It has no source. |
| **clone** | A single-use agent created by a source. It shares the source's identity and stable configuration and has its own timeline. |
| **source** | The agent that created a given clone (the original or another clone). |
| **timeline** | An agent's full, durable context: every turn, in order. An agent *is* its timeline. |
| **clone** (the call) | The source's single clone call (the model's `fork` call). It names at most one focus graft (the model's `current`) and any number of background grafts (`detached`); each entry names the skills it holds, the messages it is seeded with (pointers the source gives), optionally the source's own words for it (`reason`) and, optionally, its id. The harness validates and commits the whole call or none of it. |
| **graft** | A clone seen as one entry of a clone call. A **focus graft** takes the conversation and its source is suspended until it joins. A **background graft** runs concurrently, never talks to the user, and its source keeps the conversation. |
| **join** | The clone's final act, at the end of its turn (by its merge call, or by the harness when the turn ends without one): it raises a join event and ceases to exist. The harness then applies the deterministic default join to the source. |

"Journal" and "daughter" from earlier drafts are retired. There is no separate log; the timeline is the record.

### What the model is told: fork, merge and stop

The words above are graft's own, for its harness, store and state machines. The model never sees them. To the model, a graft is **a branch of itself**, made by **forking** (its tool is `fork`), and a join is that branch **merging** back into **main**, the line the original holds. Its built-in tools are:

| Model's word | graft's own word |
|---|---|
| `fork(current={id?, skills, messages, reason?}, detached=[{id?, skills, messages, reason?}, ...])`, the tool and skill the original holds | the clone call; the clone skill |
| an entry's `messages` (row ids or short exact quotes) and `reason` | the seed's pointers, as the source names them; the source's own words for the graft, carried in its clone call |
| a branch's id (`id`) | its name (`timelines.name`), mapped to its timeline id |
| a **current** branch | a focus graft (`kind="focus"`) |
| a **detached** branch | a background graft (`kind="background"`, timeline status `background`) |
| the `detached` skill | the skill linked to every background graft (stored under the name `detached`) |
| `merge(reason?)`, the tool of the `merge` and `detached` skills; `reason` is the branch's own words to main, not a join reason | the join event; graft's join reasons (`done`, `out_of_scope`, `failed`, `cancelled`) are its own and never reach the model |
| the merge's tool result in main's view | the source's record of the join: which graft joined, whether the user saw its replies, which grafts still run, and what to do next |
| `stop(ids=[...])`, the original's second tool | graft's cancel; the join reason it sets stays `cancelled`, the harness's own |
| stopped (a branch the agent stopped) | a graft joined `cancelled` |
| `load_skill(name)` | unchanged |

Current and detached are said in git's terms in the `fork` skill: the line the original holds is **main**, and the conversation with the user is HEAD; the original stays on main whatever it forks (`current` names a new branch, never main); a current branch takes HEAD for one turn, in which the user talks to it, and when that turn ends it merges and HEAD comes back to main; a detached branch works off to the side with no line to the user. A stopped branch is stopped where it is; what it did merges back; nothing it did outside the conversation is undone.

**Fork and merge are messages.** What a branch starts with, and what main gets back, are messages a model call sees, never notes about them:

- A branch's view is the messages main pointed at (`messages`, in stored order), then main's own fork turn (the assistant message that holds the `fork` call, every entry's `reason` included, and any text main wrote with it), then that turn's tool results as the branch sees them: the `fork` call's result is the branch's own ("you are now on branch site (current), holding: website. Your part: the reason you wrote for site above."), and every other call of that turn has main's result. Main's own result stays "forked -> ...". Nothing is injected with the user role.
- A merge brings back the branch's text rows main lacks, then the branch's merge call (the last assistant turn's `merge` tool call, its `reason` included, so main's next model call sees it as an assistant message), then that call's result in main's view, which main owns and which says which branch merged; for a current branch, that its replies above already reached the user and are not to be repeated; which branches are still running; for a branch main stopped, that it stopped it and the tools it had run there; and to go on with what is still to do, forking for it, or to end the turn without speaking.

Everything the model reads says so: the skill instructions and descriptions, the tool names, descriptions and schemas, the tool results and refusals of these tools (a branch's fork result and main's merge results included), and every harness note. graft's internal identifiers (timeline ids, `kind="focus"` and `"background"`, the `cancelled` reason, the machine's state and event names) stay as they are and never reach the model: every note and result names a graft by its id as the model knows it (its name), never its timeline id; where a note or result says a reason or a kind, it says it through the one function that words them for the model (`cancelled` is said "stopped").

The framing is first person, because a graft is the agent itself and not a helper it hands work to. The original works on a request by forking itself: each branch it forks is the same agent continuing on one part, holding only the skills that part needs, with the part said in its own words (`reason`); a current branch carries the conversation with the user for one turn, a detached branch works out of sight. In a branch the model is told it is working on one part of the conversation in a branch of itself (its part: the reason it wrote for that branch), and that the other parts are being done in other branches of itself or on main. A detached branch's final reply is what it will remember of that work when the branch merges. When a branch merges, what the agent did there is in its own memory (the rows the merge appends), and the merge's result says so ("site merged; ...") and asks it to tell the user, in the first person, what it did where the user has not seen it. No model-facing text calls a graft a clone, a graft, an instance, a subagent, a worker, a helper or a delegate, calls the original "the original", says the assistant will remember something on a graft's behalf, uses the words focus, background or cancel, or uses `branch` as a tool or verb ("call branch", "branched"; the tool is `fork`, and a branch, the noun, is what it makes), or names a join reason (`done`, `out_of_scope`, `failed`: the model's `merge` takes none): the user hears one "I". A branch is told its own id, in its system prompt's per-timeline part and in its fork result.

A static check holds the wording: every function that writes model-facing text (the built-in skills, the refusals and results of `fork`, `merge` and `stop`, a branch's fork result, main's merge results, the harness notes, the compaction and seeder prompts) is on one list, and the string constants in each are scanned for the banned words; a run-time check scans what a scripted model was sent.

In the rest of this document, "clone" and "join" name graft's operations; where it quotes what the model is shown, it uses the model's words.

## Motivation

A single agent equipped with many skills can solve complex, cross-domain tasks. But as capabilities accumulate, unrelated instructions and histories share one reasoning context and influence each other. Individual skills can pass their evaluations while their composition misbehaves.

The usual fix, delegating to sub-agents, introduces a second problem: the sub-agent reports back in its own words. Every hop is a game of telephone.

Agent Grafts addresses both:

- **Isolation down:** a clone sees only the conversation rows its source points it at (text messages, never its source's tool calls, tool results or loaded skills) and its source's clone call, plus its linked skills. The source chooses what each clone sees.
- **No telephone up:** the clone never writes an account of its work for someone else to read in its place. What comes back is chosen by no one: the default join appends, by pointer, the text rows of the clone's working view the source lacks (bounded only by the join size fit) and the clone's merge call; the clone's own words (its replies, and the reason it may give with `merge`) come back verbatim as its rows, next to everything else it said, never rewritten by a model.

## Model

### Everything is SQLite

All state lives in one SQLite database. A clone is a new timeline; cloning and joining are atomic, validated inserts of pointers.

```sql
skills(skill_id, name, description, instructions)
tools(tool_id, name, input_schema)
skill_tools(skill_id, tool_id)

timelines(timeline_id, source_id, status, created_at,
          name,                                 -- the id the model knows a graft by: unique, never reused
          join_reason, join_trigger)            -- set by the join event
timeline_skills(timeline_id, skill_id)

turns(row_id, owner_timeline, role,             -- role: user | assistant
      kind,                                     -- text | tool_use | tool_result | thinking
      tool_name, content, tokens, ts,           -- stored once, never edited
      harness)                                  -- 1 = written by the harness (a note), else 0

context(timeline_id, pos, row_id)               -- pointer table: an agent's context

transactions(tx_id, timeline_id, kind,          -- clone | join
             status, committed_sql)             -- audit record of every clone and join

withdrawals(timeline_id, row_id, ts)            -- a user message withdrawn after its row was written,
                                                -- unanswered, in that conversation's view
```

### One primitive

Seeding a clone, joining it back, and compacting a timeline are the same operation: **a validated selection of pointers to existing rows**, plus new rows only where an agent writes them (replies, and compaction's compressed turns, which always record the window they condense). Stored rows are never edited, and every paraphrase links back to its originals.

### Context is a pointer table

Every turn is stored exactly once in `turns`, owned by the timeline that produced it. An agent's context is not a copy of rows; it is an **ordered, append-only list of pointers** in `context`, read through a view:

```sql
CREATE VIEW ctx_c7 AS
  SELECT t.* FROM context c JOIN turns t USING (row_id)
  WHERE c.timeline_id = 'c7' ORDER BY c.pos;
```

- **Cloning** inserts pointers for the new timeline to the rows the source selected.
- **Joining** appends pointers to the source's context, pointing at rows the clone owns.
- **New turns** are inserted into `turns` once and a pointer is appended.
- Nothing is ever copied, moved, edited or deleted. `turns` and `context` are both append-only.

Consequences:

- **No duplicates by construction.** `row_id` is the permanent identity; a join simply skips rows already pointed to.
- **Provenance is free.** `owner_timeline` records where every memory came from. The model sees joined turns natively, while the harness and evals can always trace their origin.
- **Rollback is always safe**, and earlier positions never change, so the prompt cache stays valid. The one exception is a withdrawal mark: it changes how its row is shown, once, in the views it binds, when it is written (at the end of the run that did not answer the row, when a focus graft starts for a request withdrawn before it could act, or when the graft holding it joins back), so the cached prefix is kept up to that row.
- **No table modifications** for clone or join beyond inserting pointers.

The harness is a small loop:

1. Read the active timeline's context view.
2. Resolve its tools through `timeline_skills → skill_tools`.
3. Call the model.
4. Insert the new turns and append their pointers.

### Validated views

The view is sent to the model exactly as stored. There is no hidden normalization at render time: the one stored mark that changes how a row is shown is a withdrawal (`withdrawals`, see [State machine](#state-machine)), which shows a user message its caller withdrew as withdrawn.

Instead, validity is a **commit condition** of every operation that changes a context (a clone's seed, a join). The harness validates the resulting view before committing:

- user and assistant turns alternate (consecutive rows of one role are one message); a view may start with either role: a graft whose source pointed it at no messages, or first at an assistant message, starts with an assistant turn (see [Open Questions](#open-questions) for providers that want a user turn first)
- every `tool_use` has its `tool_result`, and vice versa
- the view ends in a state the model can continue from (for a join with a trigger, the trigger is the last user turn)
- thinking blocks are either valid for the model or excluded

If validation fails, the commit is refused with the specific violations. For a `fork` call, the source gets the violations back and may call again. The deterministic default join is built to always validate; a failure there is a harness bug.

### Compaction

A timeline stores the full, uncompacted history. An agent's working window may be a compacted view over it, but the full record is never lost.

**Compaction keeps and rewrites, with provenance.** When a timeline's working view exceeds its budget, the model produces the new working view from two kinds of rows:

- **Kept rows:** pointers to original rows, preferred where rows are short or exact wording matters (names, numbers, quotes).
- **Compressed turns:** new user or assistant rows that condense several turns. Compaction is paraphrase by nature, for both roles. Each compressed row records the **window** it condenses, as pointers to the window's first and last rows:

  ```sql
  compressions(row_id, timeline_id, begin_row_id, end_row_id)
  ```

  A window is a contiguous, inclusive range in the timeline's context order. Windows never overlap each other or a kept row, so kept rows and windows partition the compacted history: every original row is either kept as itself or covered by exactly one compressed turn, which sits at its window's position. A message the user withdrew is always kept, with its mark (see [State machine](#state-machine)): a compressed turn would restate it unmarked. The summary ablation (`--compaction summary`, one user-role summary of the whole prefix) leaves such a message out of what the summary call reads, so the summary cannot restate it either.

Compressed turns render as ordinary user and assistant turns, so the model sees a natural conversation; only the store distinguishes verbatim from paraphrase. The result is validated like every other context change. Provenance means a seed can hold a compressed row while the audit trail still shows it is a paraphrase, and expanding it back to its originals is just reading the rows between `begin` and `end` (for example, a future `absorb`).

## Skills and Tools

- **Tools come only through skills.** A timeline's capabilities are exactly `timeline_skills → skill_tools`. There is no direct tool-to-timeline link.
- **Skills are the unit of scope.** A clone does only what its linked skills allow.
- Skills are rows. Creating a clone links skills to its timeline through the `timeline_skills` junction table (skills are reused across many clones).
- Skills declare no required input contract. The seed is the messages the source points at, or what the host's decisions client picks (see [Clone](#clone)), followed by the source's clone call with its own words for the clone.
- **Progressive disclosure.** A timeline's system prompt lists only the `name` and `description` of its linked skills. Full `instructions` enter context only when the agent loads a skill with the built-in `load_skill(name)` tool, as an ordinary tool_use/tool_result pair in its timeline. Linked skills' tools are declared from the start, so the tool list stays stable. A loaded skill's instructions remain in that timeline's history, which is exactly why clones matter: they start with none of the source's loaded skills. The original's system prompt carries the catalog (name and description of every skill) so it can decide when to clone.

Three built-in skills define the architecture itself:

| Skill | Linked to | Provides |
|---|---|---|
| **fork** (graft: the clone skill) | the original only | Routing rules and the `fork` call (at most one `current` entry and any `detached` entries, each `{id?, skills, messages, reason?}`), and the `stop` call (graft's cancel) that stops running background grafts. |
| **merge** (graft: the join skill) | every focus graft, never the original | The `merge` tool (`merge(reason?)`, no reason enum) and instructions: do your part, reply to the user, and merge; the turn's end merges anyway. Using it ends the turn and raises the join event. |
| **detached** (graft: the background skill) | every background graft, in place of `merge` | The same `merge` tool, with the rules for working unseen: never ask the user anything, write the result as a final reply, then merge. |

A graft learns whether it is in the background from this skill listing (`merge` or `detached`) and from its fork result, which names it current or detached; the persona is the same in both cases.

The original has only `fork`. It converses, routes and clones; every other capability requires a clone.

### Depth

**Grafts are one level deep:** only the original clones. Clones are linked to `merge` or `detached` but never `fork`, so the chain is at most `original → c7`. Several grafts side by side under the original are still one level deep.

**Nesting was tried and removed; it does not fit grafting.** Letting clones clone was implemented (strict skill narrowing, per-timeline context budgets, and rollup of out-of-scope joins past levels that lacked the skills), evaluated, and removed. A graft hands one continuous conversation to a clone that holds the whole task; splitting that task into sub-clones breaks the continuity grafting exists to keep. In the evals, models left to choose never nested. When pushed to (`clone` linked automatically to multi-skill clones), quality fell: `nested_project` 5/20 against 19/20 without nesting, `multi_part` 2/10 against 10/10, at 22–78% more cost. Part clones lost context, handed back parts they held, and sources waited on the user between parts. Records: `experiments/results/nesting-*`.

**No usage limits.** graft does not bound how much an agent branches: a run may make any number of `fork` calls (a refused call is refused with its violations, and the source may call again), a call may name any number of branches, any number of detached branches may be live at once, a part that failed, came back or was stopped may be forked for again, and a request handed back any number of times may be forked for again. Limits on how much an agent branches are the host's to enforce, not the harness's: today its lever is `close()` (after the planned API cutover, its task list and cancel). The harness keeps only the rules that make the architecture what it is (one level: only the original forks; at most one current branch; a tool beside `fork` other than `stop` is not run; a branch's turn ends in a merge; only the original stops, and only its own live detached branches) and the bounds that recover its own faults (`MAX_JOIN_ATTEMPTS`, `MAX_STOP_ATTEMPTS`, `MAX_FAULT_RETRIES`, `MAX_RECOVERIES`), end one run (its step budget, `max_steps`, and the model call's time limit) and keep a merge inside the model window (the join size fit). Guidance on doing the job well (one branch per part, never two branches on work that changes the same thing) is the `fork` skill's text, not a rule the harness enforces.

**What a hand-back still carries.** Every focus graft hands the conversation back when its turn ends. One that merged without replying to the user since the request it was made for (graft's `out_of_scope`, its own word: the model gives no reason), or that failed, hands that request back: its trigger (the user message it did not handle, never a note or a seed) ends the source's view if the source does not hold it already, and the source's run after the merge is the one that answers it (see [Join](#join)); the requests it answered whose calls are not done, the messages that reached it after its turn began, and the withdrawals it recorded, come back with it, so a late cancel is still a withdrawal. No count is kept of hand-backs or of fork calls.

## Lifecycle

### Clone

1. The source makes **one `fork` call**:

   ```json
   {"current": {"id": "site", "skills": ["website"],
                "messages": ["I run a dental practice in Austin"],
                "reason": "Build the practice's website; ask what pages they want."},
    "detached": [{"skills": ["slides"], "messages": [], "reason": "A five-slide deck introducing the practice."},
                 {"id": "room", "skills": ["calendar"], "messages": ["book the conference room Friday 3pm"]}]}
   ```

   `current` is one entry (the focus graft, which takes the conversation for one turn; at most one by the shape of the call) and `detached` a list of entries (background grafts). Both are optional and at least one is given: a call with neither, or with an empty `detached` and no `current`, is refused. With no `current` the source keeps the conversation and every graft runs in the background. An entry is `{id?, skills, messages, reason?}`: the skills to link (from the catalog in the source's system prompt), the **messages** the graft is seeded with, optionally the source's **reason** (its own words for the graft: what its part is), and, optionally, the graft's **id** (its name). An entry carries nothing else.

   **Messages.** `messages` is a list (it may be empty) of pointers to messages in the source's working view: an integer is a row id, a string is a short exact quote that must match exactly one message (whole text first, then as a part of one; the conversation nonce a rendered message starts with is not part of a quote). A message is a text row that is not a harness note and not a message the user withdrew. Each item is resolved on its own, and an item that names no message, more than one, a row the source does not hold, a row that is not a text message (a tool call or result), a harness note, or a message the user withdrew, is a violation of its entry (named by its index), so the whole call is refused; the refusal lists the source's messages with their row ids (the latest 40, each cut to its first 100 characters), so the next call can name them by id; a refusal lists at most 12 violations and how many more there were, and a model-written value in it is cut short. Repeats are dropped, and the seed is ordered as the source's view is (stored order). The rows of the clone call's own turn are never a seed pointer: they always follow the seed (below), so a quote of the source's own text in that turn is dropped. `messages` must be a list of at most 50 items; an entry whose `messages` is empty and whose `reason` is missing or empty is refused (the graft would start from nothing). `reason`, if given, is a string; it is never read by the harness: it is model-written text that the graft and the source both read, in the source's clone call.

   **Ids.** An id matches `^[a-z0-9][a-z0-9-]{0,31}$`, is not `main` (the line the original holds, as the model is told it), and is unique within the conversation (the store): no two grafts ever have the same one, so an id is never reused, even after its graft has joined. An entry without one gets a random one, 6 hex characters, redrawn while it collides with a stored name or with an id given or drawn earlier in the same call; the random source is the harness's (`Harness(names=...)`, a callable returning a candidate id, seeded in tests), and draws are made in the call's preparation (the activity of `preparing`), never in a guard. Draws are bounded (`MAX_NAME_DRAWS` per entry): a candidate that is not a valid id, or a source that keeps colliding past the bound, is an error of the preparation, so the call is refused (`preparing ──error──▶` its refusal, every transaction `rolled_back`) and `preparing` always ends with an outcome. Name uniqueness is checked against the store in `preparing`, and the commit's unique constraint on `timelines.name` backs it: a failure there is the commit's error (`committing ──error──▶ refusing`). The machine's guards read only the machine's data (its timeline ids), never the store. The id is stored as the graft's name (`timelines.name`, unique) in the clone's own transaction, mapped to its timeline id, which stays graft's own (`c<number>`, drawn in entry order: `current` first, then `detached` in order). The graft is told its id; every note, result and refusal names a graft by it; `stop(ids=[...])` takes ids and resolves them only through the names: the run (the activity of `busy`) resolves each id through the store as it builds the cancel request, before it is put to the machine, so the machine decides only timeline ids, its guards stay pure lookups of its own data, and an id no graft has is a per-id problem of the call ("no such branch"), never looked up by the machine. A timeline id the model never saw names nothing. Every outcome of the call is worded back by the id the model gave. Two entries of one call with the same set of skills are refused unless both carry ids (so the source tells them apart).
2. **The seed and the graft's view.** The source chooses what a graft sees, as a git branch is cut from the commits it is cut from: the seed is the messages its entry points at. The source's tool calls, tool results and loaded skills are never seeded, so a graft starts with none of the source's loaded skills. After the seed, the graft's view holds the source's **clone turn**: the assistant rows of the response that holds the clone call (its text, the `fork` tool call with every entry's `reason`, and any other tool call of that response; never a thinking block, which is bound to its own conversation), by pointer, and that turn's tool results: the source's result rows of every other call of the response (a `stop` call's real result, or "not executed" beside a clone call), by pointer, and, for the `fork` call, a new row the graft owns, its **fork result** ("you are now on branch site (current), holding: website. Your part: the reason you wrote for site above."; without a reason: "Your part: what the messages above ask for that your skills cover."), written in the clone's commit. The source's own `fork` result row ("forked -> ...") is never in a graft's view. So a graft's view ends on a user turn (its fork result), and starts with the first message the source pointed at, or, with no messages, with the clone turn: a view may start with an assistant turn (see [Validated views](#validated-views)). A clone call made outside a model loop (a turn its caller drives: tests, replay), whose call is not a row in the source's view, has no clone turn: its grafts' views are their seeds alone, so such a call must point at messages. If the host passed a decisions client (the **seeder actor**, `Harness(seeder=...)`), it picks the seed instead of the source's `messages` (which are still resolved and checked, so a malformed call is refused the same way, and are the fallback): for each candidate row it answers one yes/no question ("does a branch doing the new task need this message?", where the task is the part of the latest user request the entry's skills cover, said by their names and descriptions) with a confidence score, using a small decision model (v1: TypeSafe Jev). Rows at or above a threshold are seeded in view order, and the triggering user message is always seeded. Each question carries only its row and its immediate neighbours plus the task and trigger, so the decision model's context limit never binds, and large views are split into parallel batches. The seeder runs once per entry, and the entries are seeded concurrently; if one seeder call raises, the others are cancelled and awaited before the call is refused. The full decision (model, threshold, per-row scores, selection) is recorded with the clone, so seeds stay replayable. If the seeder fails, the source's own `messages` are the seed. Either way the seed resolves to pointers, never copies or paraphrases, and only to rows the source holds in its own context, and the clone turn follows it.
3. The harness validates the call and every entry's resulting view (see [Validated views](#validated-views)): the seed, the clone turn and the fork result, so a clone turn whose other calls lack a result row is refused. The input is model-written, so nothing about its shape is assumed: `current` must be an object, `detached` a list of objects, each entry with `skills` as a list of known skill names without repeats, `messages` as a list of integers and strings, an optional string `reason`, an optional `id` as above, and no other field. A call may name any number of branches, and a source may have any number of live detached branches (see [No usage limits](#depth)). **The call is one atomic batch:** any violation refuses the whole call, with the violations listed per entry (`current`, or `detached[i]` by its index in the list), and creates nothing; the source may call again. An error raised while handling the call (the seeder, a refusal by the state machine, the commit) is a refusal as well: the source always gets a tool result, every transaction of the call is recorded `rolled_back`, and no clone exists. The state machine's step and the store's commit are one unit: the machine decides the prepared call first and may refuse it, and the commit is the activity of its `committing` state, so if the single SQL transaction fails the call is refused (`committing ──error──▶ refusing`) and no graft machine is made; the machine and the store never disagree about which grafts exist.
4. On success the harness inserts, in one transaction, every graft's `timelines` row, its seed and clone-turn pointers into `context`, its fork result row, and its `timeline_skills` links. The `fork` call's single result names every graft by its id ("forked -> site (current; ...), 3fa9c1 (detached, running; ...)"), so the source knows what it did.
5. With a focus graft, the source enters the **cloned** state: suspended, its timeline does not grow. The focus graft becomes the active leaf and talks to the user.
6. Without one, the source stays **active**, tells the user what it started, and keeps the conversation.
7. Background grafts start in the **background** state and run concurrently (one made for a user's call that was withdrawn meanwhile never runs: it joins `cancelled` at once; see [State machine](#state-machine)).

**A graft does only its own part.** A graft has its seed, the source's clone turn with the reason written for it, its id and its skills. When the request has several parts, grafts may be seeded with the same messages, so the rule is in the `merge` and `detached` skills and in their one-line descriptions: do the part the reason you wrote for this branch gives you (or, without one, the part your skills cover), leave the rest to the other branches of yourself and to main, and never hand the rest back. The source therefore needs one entry per part.

A clone inherits the source's stable configuration (persona, model, global policies). It inherits conversation history only through its seed and the clone turn: the text rows the source points at and the source's clone call, never the source's other tool calls, tool results or loaded skills.

**The system prompt has exactly two parts:**

1. **Persona:** the system prompt the user provides (identity, tone, policies). It is identical and verbatim on the original and every clone, and comes first so all timelines share one cached prefix. A clone *is* the agent, so it sounds like the agent.
2. **Skill listing:** the progressive-disclosure list (name and description) of the timeline's linked skills; the original also gets the catalog. **This is the only part that differs between timelines.**

Architecture rules (routing, cloning, joining) are not part of the persona; they live in the `fork` and `merge` skills and load through progressive disclosure like any other skill.

### Join

1. **Every turn of a clone ends in its join.** The clone calls `merge(reason?)` (the tool of its **merge** skill; a background graft's **detached** skill has the same tool), which ends its turn: any other tool call of that response is answered "not executed: this branch is merging" and is not run, and the call's own result in the clone's timeline is "merged". The call takes no join reason: its optional `reason` is the clone's own words to its source, which the source reads in the merge call itself (below); the harness never reads it. Its input is model-written, so it is checked, never rewritten: a merge call whose input is anything but `{}` or `{"reason": <a string of at most 2000 characters>}` still ends the turn, but its result is a refusal naming that rule, so it is not the call the source reads, and the join writes the harness's own `merge()` instead. A fork entry's `reason` has the same bound (a longer one refuses the call). A turn that ends without a merge call (a reply with no tool call, an empty response, a spent step budget, a run that raised, a stop) joins all the same, **implicitly**: the harness writes an argument-less `merge()` call at the end of the clone's timeline, marked as the harness's (`harness = 1`), with its "merged" result, so every join has the same shape in the store and in the source's view. That write is the join's own (see [Default join](#default-join-deterministic)): it is made in the join's single SQL transaction, before the source's pointers, unless the clone's timeline already ends on a merge call and its "merged" result (a merge call of an earlier turn, closed as not executed, does not count), so a retry writes it once and a join given up never writes it. A focus graft therefore holds the conversation for one turn: the run that answers the request it was made for. If that request is withdrawn (its task canceled), the turn ends there and the graft merges `cancelled`, whether its run was cut short or it never ran, so the conversation always comes back to main. A turn a fault ended (a run of its model loop had begun since it was last at rest, no withdrawal or shutdown cut that run short, and it is not shutting down) joins `failed` (see [Internal faults](#internal-faults)); a fault while it never ran, in a turn its caller drives, or while it shuts down leaves it at rest, as without the fault. Two endings do not join: a turn its caller drives (`begin_turn`/`end_turn`: tests and replay end it themselves, and may raise its join with `do_join`), and a turn cut by shutdown (the harness is closing: a suspended source closes with its focus graft shut down, as before). Its replies are already rows in the store and were said to the user as they were written (see [User Experience](#user-experience)).
2. The harness raises a join event. Everything after this is a deterministic state transition, with no model call:
   - focus graft: `active → queued` (frozen permanently, its join last on the source's queue); source: `cloned → joining`. When the join has been written to the source: `queued → joined`.
   - background graft: `background → queued` (frozen permanently, its join waiting on the source's queue), then `queued → joined` when the join is applied to the source at rest (see [Parallel grafts](#parallel-grafts))

   The state machine is asked first. If it refuses the join event (the timeline is the original, or has already raised its join event), nothing is written: a second join never changes a graft's recorded reason. The reason and trigger travel with the queue entry and are written to `timelines` once the event is accepted.
3. The join event carries only harness-generated fields, never clone-written text:

   ```text
   {clone: c7, reason: done | out_of_scope | failed | cancelled, trigger: <row_id> | null,
    closing: {<tool_use_id>: (<result>, <is_error>)} | null}
   ```

   `closing` is the graft's close-out it could not write as it froze: when a graft's run ends early (cancelled, shut down, or failed) its open tool calls get results as it records its join (a background graft's `recording`, a focus graft's `failing`); if that write fails, the graft's machine keeps those results (the real result of a call that ran, "cancelled while running" for a tool cut short where it waited) and carries them with its join instead of dropping them, since a frozen graft never writes to its view again. The source writes them into the graft's own timeline in the join's single SQL transaction, before the join's pointers and merge result (`applying`), so the graft's view is valid once its join lands and its merge result lists every tool it ran. Only results its last turn still lacks are written, so a retry after a failed join write, which left nothing in the store, writes each once. A call it does not name is closed as not executed. A join that is given up (`abandoned`) never writes it, so the graft, as it is abandoned, has the scribe write its carried close-out into its own timeline (a write that fails is told once, as a harness error event).

   The **reason** is graft's own, set by the harness from how the turn ended, never by the clone: `done` (a merge call or a reply ended the turn: a focus graft that replied to the user since the last user message in its view, or a background graft), `out_of_scope` (a focus graft whose turn ended without such a reply: the request comes back to its source, which answers it), `failed` (the run raised, timed out or spent its step budget; a background graft's empty response), and `cancelled` (the original stopped a running background graft, see [Parallel grafts](#parallel-grafts), or the request a graft was made for or holds the conversation for was withdrawn, see [State machine](#state-machine) and [Cancel](#cancel)). The model never sees a reason: what the source reads is the merge's result, worded from it (below).

   `trigger` is the user message the clone did not handle, if any: the last user message in its view when it hands it back or never answered it. A harness note is not a user message and is never a trigger. A background graft never receives a user message, so its trigger is always null.
4. Mechanical failures (errors, timeouts, exhausted budget) raise `failed` without the model. A model call has a time limit (300 seconds by default, configurable, and it can be switched off); a call that does not return in time is such a failure, so a hung call cannot keep a graft live for ever. This holds for a focus graft as for a background graft: if its run raises, it joins `failed`, its source takes the conversation back and answers the user, and the error does not escape as an exception from the user's turn.
5. **A graft always joins.** A background graft's turn is its whole run: a turn that ends on a text reply without a merge call joins it `done` (the reply is its result), and an empty response joins it `failed`. A focus graft's turn that ends without a merge call joins it as in step 1, `done` if it replied to the user, else `out_of_scope`; a spent step budget joins it `failed`.

### Default join (deterministic)

When a clone joins, the harness applies a fixed default with no model call, then validates it like any other commit:

Every join appends to the source, in order: pointers to the text rows (user and assistant) of the clone's **working view** that the source does not already have; a pointer to the clone's **merge call** (the `merge` tool call of its last assistant turn, the model's or the harness's, never the other calls of that turn, which stay in the clone's timeline); and the **merge result**, a new tool-result row the source owns (marked as the harness's) that pairs that call in the source's view. Then, if the clone handed back a user message the source does not hold, the trigger. What differs by reason is only the merge result's wording:

| Reason | The merge result says |
|---|---|
| `done`, a focus graft | which branch merged; that its replies above already reached the user, so they are not to be repeated |
| `done`, a background graft | which branch merged; that what it did there is in the messages above and the user has not seen it: tell the user, in its own words and in the first person |
| `out_of_scope` | which branch merged; that it merged without answering the user's last message, which is the source's to answer now |
| `failed` | which branch merged; that it failed, and what it did before it failed is in the messages above |
| `cancelled` | which branch merged; that it was stopped before it finished (by the original, or because the user's call it was made for was withdrawn), naming the capability tools it had already executed, including any that returned an error (marked as such), that nothing it did outside the conversation was undone, and to tell the user so |

Every merge result also names the source's grafts still running (with their skills) or says none are, says that still-running work is not to be described as finished, says that rows the size fit left out stay in the clone's frozen timeline (when it left any out), and ends: go on with what the user asked for that is still to do (forking for it), unless a still-running branch is already doing it, or end the turn without saying anything if nothing is. It never forbids forking. A join appends no other row.

- The **working view** is the clone's context as it would be sent to the model: the full conversation if it never compacted, or its kept and compressed rows plus the turns after the last compaction if it did. The join is therefore bounded by one context window, and it is what a single agent would have remembered had it held the conversation itself.
- Compaction is the agent compressing its own memory, with every compressed row pointing at the window it condenses, not a worker reporting to someone else, so it does not reintroduce the telephone problem.
- Tool calls, tool results and thinking stay in the clone's frozen timeline, except its merge call, which the source points at.
- The source then returns to `active`, and **always runs once after a merge** (unless the user's call it would answer was withdrawn, or a message is waiting, which its own turn answers with the joins in view: see [State machine](#state-machine)): in a turn on a handed-back message if that message is now its last row, otherwise in a wake, whose view ends on the merge results. That run is a full run, like any turn: it may answer, clone, cancel and go on, or end without saying anything. After a focus graft's `done` join that is how the source picks up the rest of a request the graft did not do; after `out_of_scope` or `failed` it answers the request that came back.
- **One join is one SQL transaction:** the clone's close-out and its implicit merge call (rows of its own timeline), the pointers, the merge result row, the trigger pointer and the outcome of the join's audit record are written together or not at all. A join that fails halfway leaves nothing in the source, its audit record says `failed`, and it can be retried without duplicating anything. The write and the state machine's step are one unit: the graft becomes `joined` only after the write, and if that step fails after the write, the retry finds the join in the store, writes nothing, and completes the step.
- A clone may merge without a reply: a focus graft that does hands its request back (`out_of_scope`), and a background graft's result is then only what it wrote before.
- A background graft's join is the same default: the text rows of its working view that the source lacks. Its seed and the clone turn are rows the source already holds, so they are skipped.
- If the source's resulting view would be invalid (cannot happen for well-formed rows; a harness bug), the join appends a harness note saying the branch merged but its rows were skipped, and the trigger, and its audit record says `rolled_back`. That note is one of the two harness notes left (the other is the withdrawal mark, see [State machine](#state-machine)): there is no tool call there to carry the text.

A suspended source leaves `cloned` through its focus graft's join event (a clone call that could not be committed never reaches `cloned`: it is refused while the source is still in its turn). Joins are applied during `joining`, which always returns the source to `active`.



### State machine

The state machines (stateforward `hsm`) own all of the coordination: what may happen, who waits, and in what order. The harness holds no lock, no task of its own and no future except a reply carried in an event's data; it does only I/O for the machines (model calls, store reads and writes, tool execution, emitting text, building prompts). A run of the model loop is the activity of the machine state it belongs to: leaving that state ends the run, and the library awaits its end inside the same step, before the transition's effect. Machines talk only by events: an effect forwards an event to another machine. A caller outside the machines (a host's message, cancel or wait for events, `close`, a clone or cancel call made by a model loop) gets its answer either as a response event or from a future carried in the event's data, which an effect resolves; the future only carries the answer, and the graph decides who waits. Decisions are guards and choices, and the guarded branches of a choice (or of one event's transitions from one state) are disjoint, so no outcome depends on the order they are declared in: one unguarded default takes the rest. An effect only changes its own machine's data, answers a reply carried in the event, and dispatches at most one event. A step that has more to send goes through states: a chain of choices with one send per transition (giving up a join: the repeat of the commit failure, the abandonment line, the graft's `join abandon`), or a state that ticks once on entry and a choice that sends the next item (the failures of a background graft's `recording`, the cancel result rows that could not be written, the stops of the background grafts made for a withdrawn request), so the reply a caller waits on is answered last. Everything that can fail is the activity of a state: a clone call's preparation (`preparing`: seeding and validation) and its rollback when the run is left while it is prepared (`unpreparing`), every store write (a user message's row in `requesting`, a clone call's commit in `committing` and its result row in `recording`, a refused call's audit in `refusing`, the cancel results in `writing`, a run's open tool calls in `closing_calls`, a withdrawn request's mark in `dropping` and `withdrawing`, each join in `applying` (its merge result included), a background graft's join reason in its own `recording`), starting graft machines (`spawning`, which awaits each start), a host tool call (`calling`), its result row (`storing`), and the lines and trace the user's callbacks receive (the scribe machine's `writing`). The activity ends by dispatching its outcome as an event; if it raises, the library dispatches `hsm/error`, and every such state has a transition for it. No activity ends without an outcome, and one rule tells a cancel apart in every activity: a `CancelledError` means its state is being left only when the activity's context is done (the library marks it before it cancels an activity, which it does only when the state is left), and is then never swallowed; any other cancel (a host's or a provider's own, surfacing in a call the activity awaited) is the activity's failure, like any other error, and the task's cancel requests are withdrawn; it is carried as a `RuntimeError`, so a caller that gets it as its reply never takes it for its own cancel (and never withdraws its request for it). The library tells only an `Exception`, so whatever else an activity raises (but a cancel, or `KeyboardInterrupt` and `SystemExit`, which asyncio lets out of the loop) is raised as one (`Aborted`) and taken by the same transition, or is the activity's own named outcome where it has one (a run's `run_failed`, a tool's result, a row write's `tool_unstored`, a graft start's `spawn_failed`). A run of the model loop is the one activity whose failure is its own event (`run_failed`, whatever it raised but a cancel or the interpreter's own exits): states inside the run have activities of their own (a clone call's preparation, a step's writes), whose `hsm/error` they handle as their own failure, so the run's failure is never taken for theirs. A clone call being prepared when the run fails is cut short and rolled back (`unpreparing`) and the run's failure is then handled as anywhere in `busy`; a step finishes first. A guard, effect, entry or exit is not meant to fail; one that raises is a fault of its machine, recovered from in the graph (see [Internal faults](#internal-faults)). No write sits between a machine step and its closing event: the write is the activity of the state that the closing event leaves, so the machine cannot move on before the write's outcome is known, and cannot stay in that state after it, whether the write succeeded or failed. A clone call's grafts are started (`spawning`) before anything else learns of them, the focus graft last (it starts on its request at once, so it is made only once every background graft of the call has started); if one cannot start, the machines made are stopped and forgotten, the committed grafts are marked abandoned, the session forgets them (`grafts_undone`), so nothing an undone graft told it stays, and the call's result is a refusal.

**A user's call is a request the original's machine owns.** A host's message (A2A `SendMessage`, see [Host Interface](#host-interface-a2a)) becomes one request (an id, the text, its task, and a reply future the machine answers, which no caller awaits: the host reads the event log), which the session puts on the original's machine once the task's event is written (a step its message sets off that fails answers that reply with the error, and the request's task is told the error and fails). The machine holds the request in its own data from arrival until it is answered or withdrawn, wherever it is: waiting (the inbox), its row being written (`requesting`), the request a run answers (its turn, the joins and the wake that follow it, a run that answers it after a focus graft hands it back), a caller waiting at rest, or handed to a focus graft with the conversation. A request is live while it is not withdrawn and its reply is not done. A cancel of its task (`CancelTask`, decided by the session) withdraws the request by id (`withdraw`), at any point until the task is terminal; a host that stops waiting withdraws nothing. The withdrawal is handled in every state of the original's and a focus graft's machine, never ignored: it is recorded while the machine holds the request (the record keeps no id of a request that has left the machine, so it stays bounded), a waiting message is dropped and answered at once and never taken, a suspended original forwards it to its focus graft (also while the clone call that makes the graft is in flight, when the original still holds the request and records it too; while the grafts' machines are being started, `spawning`, it waits for them, and every graft is made with the withdrawals recorded before), and a frozen focus graft, which has handed every request back, holds nothing to record (a request it handed back reaches its source, whose record holds the withdrawal). A run answers at most one request (its turn's message, the one its source answered when it was made, or one handed back), and one rule decides whether a withdrawal ends it: that request is withdrawn. A run whose request is withdrawn ends (its open calls closed); one in a clone or cancel step ends once the step is done. Every point that would start a run or let a graft act for a request is guarded on it being live: the row written (`requesting` → `busy`, else to rest: the row stays, a user turn the next message joins), the next waiting message (`rest`, `after`: withdrawn ones are dropped and answered), the wake and hand-back runs (`after`), the clone gate, a focus graft's start (a focus graft whose request was withdrawn before it could act never runs: it marks the request's row, `withdrawing`, and merges `cancelled`), and a background graft's start and each of its steps. A background graft is made for the request the run that made it answers: if that request is withdrawn before it is answered (in the clone step that makes the graft, or later while the user's call still waits), the graft never starts, or is stopped by the original once it stands after recording the withdrawal (before the answer, or after it while the call is not done: the cancel wins): at once if it is at rest (`idle`, or `cloned` under a focus graft), and otherwise as soon as the run in progress ends (`rest` stops them before it takes anything else, a waiting message included). The original stops them as its own steps, one `cancel` per step (a state that ticks once on entry and a choice that sends the next stop, `stop_one`), as a `cancel` call does, so no graft's answer is needed for the next stop and a stop whose step fails is made again, at most 3 times for one graft: a stop that keeps failing is then given up and told once, the source goes on to the next graft, and that graft stops at its next step instead; a host tool the graft awaits in `calling` is cancelled where it waits and recorded as run with an error. A late withdrawal that comes while an unrelated run is in progress therefore stops its grafts when that run ends. As a backstop the graft also stops at its next step (it asks its own machine, which reads the reply its caller cancels at once, and then its source, which stops it, `cancel`, once the request is withdrawn by its record). Either way it joins `cancelled` without a model call or a tool call after the cancel; its join is applied like any other, and wakes nothing. A graft made for a request that was answered, and whose call took that answer, goes on and is reported when it joins. A graft that joins at once in the clone step that makes it is queued after that step, once its source knows it made it; if that step is undone because a graft could not be started, its join is never applied (the source applies only joins of grafts it holds). Whether a run may go on is the machine's decision as well: before every step that could act (each model call, compaction calls included, when such a call returns, after each text it says, before each tool call and before the response's cancel calls) the run asks its machine (`may_continue`, a reply in the event's data), and the machine answers while the request the run answers, if any, is live (not withdrawn, reply not done). Once it is withdrawn, the machine leaves `busy` the way a withdrawal leaves it, which ends the run where it waits: a response that came back is not stored, said or acted on, nothing more of a response is said or run, and the calls it stored are closed as not run. A run starts inside a machine step, so its first question is answered in that step and its answer reaches the run only after the step, by which time a caller cancelled in that same step has withdrawn its request and the run has been ended; every later question, the one before the first model call included, is answered in the step the run acts in, so a cancel at any earlier moment is seen. Every other point is a machine step, where the withdrawal is handled. So a withdrawn request never causes a model call, a tool call, text or a stored row after the cancel. A withdrawn request whose row was already written and that no run answered is closed out in the store: the row gets the withdrawal mark (`withdrawals`; the row itself is never edited), written by the state that learns of it (`dropping` when it was withdrawn while its row was written; `withdrawing` when the run answering it is cut short, when a focus graft starts for it after it was withdrawn, or when a focus graft handed it back and no run will answer it). A mark that cannot be written is told to the user once and stays to be written, in the machine's data: whatever next reads that view writes it first (a run of that timeline, its compaction, seeds and seeder included: if the write fails again, the run fails before it reads anything; a clone call's preparation, in a turn its caller drives too; a join's copy into the view), a focus graft hands it back to its source with its join, and a recovery (see [Internal faults](#internal-faults)) writes it. The mark binds the views of the conversation it was asked in: the timeline that holds it and, for a focus graft, its source, which gets the graft's rows back by its join. There the row is shown to the model as a withdrawn message, marked like a harness note, and is never a request, a trigger or a seed candidate, so no later turn or hand-back reads it as live user text. It is never seeded either: a pointer to it is refused, the seeder's candidates leave it out, and every entry's final seed is checked for it before the call commits. Compaction keeps it with its mark: the compaction call's index marks it, and a window that would compress it is refused; a summary compaction leaves it out of what the summary call reads. The mark does not bind the view of a background graft seeded with the same row before it was withdrawn, which is not that conversation: only the request a run answers can be withdrawn after its row is written, so that graft was made for it, and it stops (see above). A request its turn answered before the cancel (the joins and the wake that follow the turn) is not marked. **A cancel after the answer wins.** A cancel that lands after the machine answered the request (its turn ended, its task is not terminal) is a withdrawal like any other, and the machine honours it while the request is not done. It keeps each request it answered at rest until the session says the request is done (`call_done`, which the session sends when the request's task becomes terminal; a suspended original passes it to its focus graft, and a focus graft hands back with its join the requests it was given, which its source answers when it comes to rest after the merge, its wake included), and a background graft's request until the graft's join is applied. A withdrawal that reaches a focus graft once it is frozen changes nothing there; the source decides on the request by its own record or by its reply , whichever comes first. The withdrawal is recorded by the machine that knows the request (the original, if it made background grafts for it, else the timeline that answered it): the background grafts made for it stop before their next step and join `cancelled`, their joins wake nothing, nothing more is said or done for it, and its row gets the withdrawal mark in that timeline's view (and, for a focus graft, its source's), a write of the scribe's (one that fails is told, as a harness error event). A wake that reports only background grafts made for withdrawn requests does not run, or ends. A request whose reply a recovery failed is kept the same way, as answered. An error the request was answered with is its task's (told on it once, by the session); text said for it before the cancel stays in the event log. A withdrawal of an unknown id, or of one whose call is done, changes nothing.

A background graft:


Leaving `background` ends the run first, whatever the event, so a graft is never `queued` while its run still goes, and there is one closer: `recording` writes the join reason (its activity), tells the user of each write that failed, one per step, and then forwards the join to the source. A graft that was about to finish when it was cancelled cannot race the cancel: the graft's machine takes one of the two events, and the other finds it `queued` and changes nothing.

The session machine (one per harness) knows whether anything is in flight: the original engaged (running or applying joins), or a background graft whose join has not reached its source. It owns the host's tasks and the event log's consumers (see [Host Interface](#host-interface-a2a)); `close` is `shutdown`, which it forwards first to the original (from then on nothing is woken), then to every background graft still running, and, once all their joins have reached the original, to the original again, which applies what it can and closes. A clone call that was already past the original's gate when closing began may still make grafts: the session shuts them down the same way when it learns of them, and the original, shut down while a graft of its own still runs, waits at rest for that graft's join before it closes. Its record of each timeline (engaged, and for the original its background grafts whose joins have not reached it) is kept by the events the timelines send it, and re-stated whole by a timeline that recovers from a fault (`resync`); a fault of the session's own steps has the original re-state its record, and, while the original is suspended, its focus graft with it.

`queued` means the graft is frozen and its join event, with its reason and trigger, is waiting on its source; `joined` means that join was applied to the source. A focus graft and a background graft go through the same two steps. Both states are recorded in `timelines.status`, so a join that has not landed is never mistaken for one that has. The queue belongs to the original's machine, in finish order; it changes only in effects, and a graft leaves it only when its join has been applied or given up.

**The state machine is the authority.** The graph refuses a clone outside a turn or wake, from a graft (grafts are one level deep), or with more than one focus graft; a join from the original, or a second time; a cancel from a graft, from the original when it is not running, or of anything but a background graft of its own whose join has not been raised. Joins are applied only from rest: when a graft's join arrives at an idle original, at the end of a run, before a user message that waits, and when a focus graft joins back. The harness never reads a machine: what it needs for a run or a note (the timeline's kind, the source's grafts still running, whether the clones named are background grafts) comes in the host call the machine's activity makes, and tests observe only replies, the calls the machines make to the host, and what is stored (a machine's record of withdrawals included: it is observed by what it decides, a message whose request reuses a withdrawn id). The clone rules are the machine's, in two steps around the seeding. Before anything is seeded, the machine's gate on the whole call refuses it while the harness is closing, while the request the run answers is withdrawn, or from a graft. Then the harness prepares the call (the activity of the machine's `preparing` state): it checks the call's shape, including at most one focus entry, and seeds and validates every entry. Then the machine decides the prepared call: new timeline ids (from its own data; names are the preparation's, see [Clone](#clone)), and at most one focus graft. A join that cannot be applied, a focus graft's as much as a background graft's, stays `queued` with its reason and trigger; the user is told at once which clones are affected and that the commit failed; the original returns to rest holding the conversation; and the join is retried at the next commit point, not at once. A handed-back user message is still answered once its join lands. The retries are bounded: after 3 failed attempts the join is given up, the graft ends `abandoned`, the user is told once that its work is not part of the conversation's memory, and the joins behind it are applied.

**An interrupted turn leaves a valid view.** If a run ends (a withdrawal, an error, shutdown) after a tool call was stored and before its result was, every tool call of that last response that has no result gets one: a result saying the call was not executed, or, for a call that did run (a tool, or a cancel call) and whose result alone could not be written, its real result, which the machine kept (the run hands it to its machine before the write's error ends the run, so a tool that ran is never recorded as not run). A clone call's open transactions are closed as `rolled_back` (by `unpreparing` when the run is left while the call is being prepared: if that rollback fails, it is told as a harness error event). The next model call on that timeline is well formed: a clone call whose result row, or refusal row, cannot be written ends its run with that error (the user is told, and the call's caller, the run, gets it), so no model call reads a view without that row, and the run's closing writes the row it kept. Each tool call's result is stored as soon as that call returns, so a later call of the same response that raises never leaves a call that ran recorded as not run.

**A host tool call is the activity of a state.** The run does not execute a capability tool itself: it asks its machine (`tool_request`, a reply in the event data), and the machine's `calling` state (inside the run: `busy`'s run, or a background graft's `running`) makes the call as its activity. A host's tool may return its result or an awaitable of it (a host tool may be an `async def` function, see [Tools](#tools)): an awaitable is awaited in that activity, so while one timeline's tool waits, every other timeline's model calls, tools and joins go on, and one graft's tool may wait for what another graft's tool produces. The activity only invokes the tool; its outcome (`tool_returned`) carries the result, which the step that takes it keeps with the call, and `storing` (a state of its own, inside the run) writes the row as its activity before the run is answered (its outcome is `tool_stored`, or `tool_unstored` with the write's error). The run asks for one call at a time, after its `may_continue` for that call, so a response's results are stored in call order, and the rules for calls beside `fork`, `cancel` and `merge` are unchanged. Leaving the run (its request withdrawn, a cancel, shutdown, a fault's recovery) leaves `calling` and so cancels the tool where it waits (the tool sees the cancellation; graft never swallows it). Cancellation is cooperative: a tool that swallows `CancelledError` and keeps waiting blocks its graft's cancel and `close()` until it returns, and work a tool handed to a thread (`asyncio.to_thread`) or shielded may still act after the cancel, which is why the call's result says it may still act; a withdrawn request therefore gets no row after its withdrawal from the call. A background graft whose request is withdrawn is stopped by the original when it records the withdrawal (see the withdrawal paragraph above), so a tool it awaits is cancelled then too. A call cut short that way may already have acted, so it is never closed as not executed: before the tool is called, the activity keeps the call with the machine's other known results as run with an error ("cancelled while running: it may have acted, or may still act"), the run's closing writes it, and a cancelled graft's merge result lists it among the tools it executed, marked as returning an error. A tool that is cancelled while its state is still active (the host cancelled a future or task the tool awaited, a sibling graft's cancel included, or the task the tool runs in: only the state's own context being done, which the library marks before it cancels an activity, means the state was left) has not been cancelled by its graft: its call gets a result marked run, with an error ("cancelled by the tool: it may have acted"), and its run goes on; the cancellation that leaving the state makes is never taken for this. Once a tool is invoked it has run, whatever follows: a tool that raises (after acting, or at its own deadline; any exception, also one that is not an `Exception`, but for the interpreter's own exits, `KeyboardInterrupt` and `SystemExit`, the only exceptions asyncio lets out of the loop; a `GeneratorExit` is the tool's outcome like any other) or returns anything but (text, is_error) gets a result marked run, with an error naming what it raised or returned ("raised TimeoutError: ...; it may have acted"), a cancelled graft's merge result lists it, and its run goes on, so the model never redoes a side effect it was told did not happen; the call's trace line is written by the scribe, so a trace callback that fails never touches the result. A failure of the harness's own call after the tool was invoked (`calling`'s error) keeps the call as run too, with an error ("failed after it was invoked: it may have acted"), its row is written (`storing`) and its run goes on. Only a step of the machine that failed before the tool was invoked (its activity then holds back) closes the call as not executed. Once the tool's outcome is taken, its real result replaces that kept one before the row is written, so a result row that cannot be written, or a run left while it is written, closes the call with its real result (a write's failure that comes after the run was left is still told, once); a row that cannot be written ends the run. graft sets no time limit on a host tool call: a tool that waits is the point (it may wait, for example, until another clone files its result), and the host owns its deadlines (an `asyncio.wait_for` inside its own tool, say). A tool that hangs is still stoppable: the original's `cancel`, a withdrawal of the request, or `close()` ends it where it waits, and the call is recorded as run with an error.

**Invariant: at most one branch holds the conversation.** Exactly one timeline is `active` or `joining`: the original, or, while it is `cloned`, its focus graft. Every other timeline is `cloned` (suspended), `background` or `queued`, or `joined` or `abandoned` (final). A user message always goes to the original's machine, which answers it, keeps it until the run in progress is done, or forwards it to its focus graft. Messages are answered in arrival order: when the original hands the conversation to a focus graft, the messages waiting on it go to the graft first, ahead of any forwarded later; a focus graft that joins hands any message it never got to back to the original, in order. Creating a background graft does not move the conversation, and neither does its join.

**Exactly one timeline talks to the user:** the original, or its live focus graft (`original → c7`). A source has at most one focus graft at a time, because it is suspended while that graft lives.

### Internal faults

A guard, effect, entry or exit of the machines that raises is a bug in graft's own code (whatever it raises, an `Exception` or not, but `KeyboardInterrupt` and `SystemExit`: no step escapes the graph): sends between machines never raise (a send to a stopped, unstarted or forgotten machine is lost, not raised), and every I/O is an activity with its own error transition. The library (stateforward `hsm` 1.3.11) turns only an activity's failure into `hsm/error`, so each guard, effect, entry and exit is run so that nothing it gated acts and its failure is recovered from in the graph. The contract:

* **Guards are pure.** A guard reads the machine's data, the event's payload and the state of the reply futures it carries (read when the decision is made: a caller cancels its reply at any moment), and writes nothing. The clone rules, which work out reasons from the run's record, are worked out as data by the step before each gate (`judge_call` before `clone_gate`; the prepared call's verdict as it is taken), with any error they raised, and the gates' guards read that outcome. A guard that raises does not hold; it records, sends, reports and answers nothing. Every branch that acts (commits, starts a graft, starts or continues a run, takes a message, applies a join) is guarded positively, and every decision has an explicit unguarded branch, the safe one: refuse (the clone gate refuses the call, the prepared gate rolls the call back), stop (a run's `may_continue` ends the run, a background graft's start or next step stops it, joining `failed`), keep (a join no guard placed is kept for the recovery), or rest. That branch's effect checks that none of the decision's guarded branches held (it reads them again, as the decision read them, in a step that handles a fault too): if one did, a guard raised and changed the decision, and the effect reports it as a `DecisionFault` naming the guard (a precomputed error, from the clone rules, is raised by the branch that declines the call as itself). Each decision has its safe branch at its own level, so a guard that raises never lets the event fall through to an ancestor's transitions (a withdrawal while a clone call is prepared, for one: its safe branch records it, and a guard that raised there is a fault of the timeline, whose recovery ends the run and rolls the call back). A guard that raised where its branch was not the one to take changes nothing, and nothing is reported: nothing it gated acted, and a guard can record nothing.
* **One event per behavior.** An effect, entry or exit sends at most one event, and its sends are made only when it returns: one that raises, or sends a second, sends none of them, and its one event is its fault. The sends a behavior makes belong to its step alone (they are held per thread and per task, never in shared data), so harnesses on separate threads, each with its own loop, never send through each other's steps. That fault is the machine's data (written by the behavior that raised), and it is sent to the machine as one event of the error kind (`fault`), so it is the next event the machine takes: nothing else is taken between the failed step and its recovery, except that a fault that comes while a clone call's graft machines are being started (`spawning`) waits for the start's outcome, so no machine is left half made. Once a step has failed, no guard of it holds (its decisions take their safe branch on purpose), every activity it enters does nothing (no model call, tool, row, commit or graft start), and no event of the step reaches the session (it would see part of the step). Whether the step in progress has failed is read only by the plumbing that runs the graphs' guards, behaviors and activities, and by guards: no effect, entry, exit or activity reads it. A decision whose safe branch would act otherwise has a branch for a step that failed: such a step comes to rest without answering its callers (they wait for the recovery), and a clone call it committed is undone instead of starting its grafts (`spawn_gate`). One failure is one fault, however many behaviors of the step raised it.
* **A call's step fails alone.** A step that only took a call from outside (an internal transition: a message stashed behind a run, a withdrawal recorded, a message forwarded to a focus graft) touched nothing else, so its fault (`call_fault`) is recovered from where the timeline is (the session's request for the timeline's record whose step failed is answered again, with that step's errors): that call's caller gets the error (its message leaves the inbox), the session gets the record as it stands, and the run in progress, if any, goes on. The caller is every reply the call's event carries, read from its payload (a user's message, a consumer's `events_wait`, a clone call and the cancel calls it brought, a run's `may_continue`), whatever the event: a clone or cancel request from a run whose step failed is answered with the error, so that run ends with it (`run_failed`, handled as any failure of the run). A join that arrived in that step is queued.
* **A timeline recovers to rest.** From anywhere in `live`, any other fault leaves for `recovering` (leaving a run ends the run, and any clone or cancel request the run held is answered). A clone call whose step failed before its grafts were started is undone first, as when a graft cannot start; grafts already started stay the original's (the recovery records them from the step's event if the step did not: a focus graft among them holds the conversation, and the user's calls it was made with stay its own). What else the failed step's event brought is kept too, once (a step that failed after it kept it changes nothing): a graft's join goes on the queue, a focus graft's join brings the conversation back as when it is taken, and a shutdown still closes the timeline once it is at rest. Grafts a cancel stopped whose joins had not come when the step failed stay its own: they no longer count as live, and their joins are applied when they come. `recovering`'s activity closes out what the step left open (if that write fails too, what it could not write is kept, and written first by whatever next writes to or reads that view at rest: a message's row, a run's start, a join's copy, a mark, the next recovery, and the timeline's close; so no row lands after a tool call left without its result; a run's open calls that could not be closed, a cut-short call's rollback that failed and a refusal row that could not be written are kept the same way): the clone call's open audit transactions are rolled back, the run's open tool calls get results (a tool that ran, its real result; a clone call that committed, its result; a cancel call whose step was cut short after it stopped a graft, what it did: the graft is stopped and its join is applied when it comes), and the rows of withdrawn requests still to be marked are marked. The timeline re-states its whole record to the session (`resync`: engaged, the user calls it holds, for the original its background grafts still running and the focus graft holding the conversation) first, then the callers waiting on the failed work get the error, once: the caller of the event whose step failed, the message whose row was being written, and the user call whose request no run has answered yet (its run was ended, or the step that would start it failed), unless a focus graft holds the conversation and that call. A reply answered with an error is not a withdrawal: no row is marked withdrawn for it. Every other caller waits on work the failed step did not touch: a waiting message is taken at rest, a call whose request a run answered is answered at rest. It goes on as after a run: to rest, or, if a focus graft it made holds the conversation, through the hand-over to `cloned`; a focus graft whose turn the fault ended (a run of its model loop had begun since it was last at rest, no withdrawal or shutdown cut that run short, and it is not shutting down) goes on to its join instead (`resumed` → `handing_back`, reason `failed`: a focus graft never rests after a turn), so its source takes the conversation back; its caller already has the error, so the source's run after the merge is a wake for no request (as after a retried join), whose text is told on the tasks it is for. A timeline that is suspended, frozen or closed re-states its record where it is (a frozen focus graft first sends its join if the failed step did not: the join it kept as the step's first act, or, if the step failed before it kept it, one made again from that step's event and what it still holds; a closed original's record says it closed, so `close` goes on: a step that ends in a final state other than `joined` or `abandoned` and fails has closed the timeline, so its callers are answered and its record says so). Recoveries are bounded, so a bug that raises every time never spins: a step that handles a fault is never a fault of its own. The fault is taken before anything of that step runs, and a behavior handling it that raises (in its `fault` step, or in the step that ends its recovery, `recovered`) is part of it: the fault is handled again, from where the machine now is, with that error added, and every handler is safe to run again (a caller answered is not answered twice; what was kept is kept once; callers leave the machine's data only once answered), so the first fault's callers get its error once and nothing waits for ever; past `MAX_FAULT_RETRIES` handlings (a handler that raises every time) the raise is only reported, and only the callers the failed event carries get the error. Past `MAX_RECOVERIES` recoveries in a row the timeline gives up: the session gets its record, every caller waiting on its work gets the error (also a caller waiting to be answered at rest, but one a focus graft it made holds with the conversation: a fault that comes back on the way to rest would never let it be, so it fails closed), and it goes on from rest without closing anything out (`given_up`, as from `resumed`: a focus graft it made holds the conversation -> the hand-over finishes; a focus graft whose turn the fault ended goes on to its join instead) (the count starts again with the next user message or run).
* **A background graft stops.** A fault while it runs stops it (`recording`, reason `failed`); a fault while it records its join is added to what it reports; a frozen graft re-sends its join if the failed step did not send it.
* **The session and the scribe.** A fault of the session's own steps fails its event's caller and every consumer waiting (the answer they wait on is the session's own, which the failed step may have got wrong), and has the original re-state its record (suspended, the original passes the question on to its focus graft with its own record, and the graft re-states both in one event); a state that ticks on entry is entered again. A fault of the scribe loses the note it was taking, and the session keeps the error, with the error that note was to keep, and fails the next consumer's wait with it (no event of them was written).
* **Each failure is reported once.** A caller given the error raises it, and nothing else reports it. A fault no caller was given is told as one harness error event (on every open task; a consumer that delivers it raises it). A behavior that raises while its machine handles a fault is reported the same way, as its one event: told with the fault a timeline is recovering from, carried on the record it was re-stating, or else a harness error event (the scribe's own goes to the session to keep). The one case it is not reported is a report that cannot be sent either (the scribe or session itself failing as it is told), and a guard raise that changed no decision (above).
* **After a fault the harness is usable**: the next message is answered and `close` returns (or raises what it could not stop).

### Parallel grafts

A request with independent parts ("build the site, draft the deck, book the room") is one clone call with one background entry per part. The source keeps the conversation while they run, and can also hand the conversation to one focus graft while others run in the background.

**Background grafts never speak.** Only the conversation holder's text reaches the user. A background graft's text is stored in its own timeline and reaches the source's memory through its join; the source tells the user the outcome.

**Joins are queued, and commit only while the source is at rest.** A finishing background graft freezes at once (`queued`) and its join event goes on its source's queue, in finish order. The join itself is unchanged: deterministic, pointer-only, no model call, size-checked against the source's view at commit time. A queued join commits only from rest, in the original's machine (`idle`, or right after a run), so the join never lands between a `tool_use` and its result or under a model call in flight. Nothing waits outside the machine: a user message that arrives while the original runs or applies joins is kept on its machine and answered after (unless its caller withdraws it); a join that arrives while it runs waits on its queue. The commit points are:

- **before a new user message** is appended to the source: the queued joins commit first, and the source answers the message with them in view, with no wake;
- **at the end of the source's turn**, and **when a graft finishes while the source is idle**: the queued joins commit and the source is woken (below);
- **when a focus graft joins back** to a suspended source: the background joins queued meanwhile commit *before* the focus join, so the focus graft's trigger stays the last row.

Because contexts are append-only, a late join never moves earlier rows, and the source's prompt cache stays valid.

**Harness rows are marked, not recognised.** The rows the harness writes into a conversation (merge results, a branch's fork result, an implicit merge call and its result, and the one note left, a join whose rows were skipped) each carry `harness = 1` in `turns`. Everything that must tell a note from a user message (which rows are seed candidates, what a hand-back's trigger is) reads that mark, never the text, so a user message that looks like a note is still a user message. A user message withdrawn after its row was written is marked the same way, in `withdrawals` (see [State machine](#state-machine)).

**Merge results name the grafts still running.** Every merge result appended to a source says, in harness-generated text, which of that source's grafts are still running, with their skills ("Still running: slides-1 (skills: slides)."), or that none are. A focus graft that hands a request back while background grafts are live makes this visible the same way, and the `fork` skill tells the source not to clone again for the parts those grafts are doing.

**Wake.** Every join is news (but the join of a background graft made for a request that was withdrawn, which is applied and wakes nothing): when joins commit and no user message is waiting, the source is run once, for everything committed together, on a view that already ends with their merge results, so no note is written for it. A turn's joins and a focus graft's join wake it alike: after a current branch's turn the source runs too, and may go on with what the branch did not do (forking for it) or end without saying anything; its merge result says the branch's replies already reached the user. The one exception is a wake that would answer a user's call that was withdrawn (the joins follow a turn, or a hand-back, whose every request was withdrawn): then no run starts; the joins stay committed in the source's memory, merge results included, unreported, and the source reports them only if a later turn asks. Every wake is a full run, whatever the joins' reasons: the source may reply, clone, cancel and go on, as in any turn. If the size check kept none of a graft's rows, its merge result says that what it did there did not fit and stays in its frozen timeline, instead of pointing at rows that are not there. If the wake run itself fails, the joins stay committed and the harness tells the user at once that reporting failed; this holds wherever the wake happens (after a user turn, after a focus graft's join, when a graft finishes while the source is idle, or at the next commit point after a failed one).

**Shared resources: no locking.** Background grafts run concurrently, so there can be concurrent writers to external state, and v1 has no ownership or locking model. The source is responsible for handing out work that does not collide; the `fork` skill says so. A host tool that waits for another graft's tool (an async tool awaiting what a sibling files) coordinates through the host's own state, never through graft's context: no graft reads another's rows, and what the waiting tool returns is its own result. Continuity across clones (c7 books an appointment, c8 later reschedules it) comes only through the seed: the source points c8 at the joined rows that record c7's actions, or says what it needs in c8's reason, or c8 inspects the external state itself.

**Shutdown.** Closing the harness is a request to the session machine. The original is told first, so nothing is woken from then on; every background graft still running is shut down (its run ends, and it joins `failed`), including one that never ran; a graft whose cancel is in flight finishes it and joins `cancelled`, since its machine takes one event at a time. A failed write of a join reason is reported and changes nothing else. Once every graft's join has reached the original, the original applies the joins it can without running anything and closes; one suspended under a focus graft closes with its joins still queued. No model call is started on shutdown. Once the original has closed (it tells the session, or, if the step that closed it failed, its re-stated record says so), the session stops every machine (the original is told to close by the entry of the session's `finishing`, entered again if that step fails, so it is always told; a fault of the step that stops the machines or tells their failures gives `close` the error), the scribe included, so nothing stays live; a later request is refused. A machine that cannot be stopped does not keep the others live: the rest are still stopped, each failure is shown to the user as a harness error line (each whatever showing another one raised), and `close` raises it (the one error, or an ExceptionGroup), together with anything the user's callbacks raised while the failures were shown. Leaving a run, however it is left (a withdrawal, shutdown, an error), answers any clone or cancel request it had not answered yet with a refusal, so no caller is left waiting.

**Cancel: only the original, and always a forced join.** The original's `fork` skill carries a second tool, `stop(ids=[graft ids])` (graft's cancel, as the model is told it), for a part the user no longer wants or that is no longer needed. No graft can cancel anything: not a sibling, not itself, and not while it holds the conversation as the focus graft (a user who tells a focus graft to stop another part is asking for something outside its part; it joins back and the original cancels). The tool belongs to the `fork` skill, which is never linked to a graft, and the rule does not rest on that: a cancel call is a request to the caller's own machine, and the graph refuses it from any timeline but the original while it runs, whatever tools the caller was shown.

The cancel calls of a response are one request to the original's machine, made after the response's other tool calls have their results stored. In one step it cancels each graft the graph allows (the graft leaves its live grafts at once, and `cancel` is forwarded to it) and refuses every other id; then it waits (`cancels`) until each cancelled graft's join is queued, and only then stores each call's real result. The graft's machine ends its run before anything else (the run is the activity of `background`): the model call it was waiting on is abandoned, a result that arrives later is discarded, never acted on, and a tool call left without a result gets one saying it was not executed (a host tool that was running when the graft was stopped is cancelled where it waits and recorded as run with an error: it may have acted), so the frozen timeline is valid. The graft's join is queued with the reason `cancelled` and is applied at the next commit point like any other join. A shutdown of the original's run waits on its machine while it is in `cancels`, and a withdrawal is recorded there and ends the run once the cancels are done, so a cancel that ran is always recorded with its real result.

**Cancel and clone in one response: the cancels run first.** A response of the original may carry a `fork` call together with one or more `stop` calls (graft's cancel calls). The response's cancel calls travel in the clone request itself, and the original's machine runs them first, wherever the model put them in the response; only then is the clone call gated, seeded and decided, so a cancel runs even when the clone call is then refused in its preparation. A withdrawal of the run's requests that arrives meanwhile ends the run after the cancels, and the clone call is not run. So "stop this part and start that one" is one response. If the clone call is refused, the cancels stand. The clone call's result and the "still running" lists do not name the cancelled graft. If the clone call has a focus entry, the source is suspended with the cancelled graft's join on its queue, and that join commits before the focus graft's join, like any background join queued meanwhile. Any tool call other than `stop` beside a `fork` call is answered "not executed: call branch on its own" and is not run. The original is in the middle of its turn when it cancels, so the tool result says only that the graft was stopped and that its work so far joins when the turn ends. The join brings the text the graft had written, by pointer, and its merge result names the capability tools it had already executed. A tool that returned an error is listed too, marked as such, because it may have acted before it failed; only a call the harness itself did not run is left out. Whether a call was run is not read from the wording of its result: the harness marks each result it writes for a call it did not run (interrupted, skipped beside a clone call or a join, or a tool the timeline does not hold) in the stored row, and the merge result reads that mark. The mark is not sent to the model, and it is a field of the stored result, so the schema is unchanged. There is no way to cancel a graft and discard its work: what a graft did to the outside world is not undone when it stops, so the original must see it, to tell the user what was left behind. Its merge result says the original stopped it and tells it to report that.

Everything else is a refusal in the tool result, never an error, and touches nothing: input that is not a list of one or more ids, an item that is not shaped like a branch id (`^[a-z0-9][a-z0-9-]{0,31}$`), an id no graft has (a timeline id the model never saw is one: ids resolve only through graft names), a focus graft, and a graft that has already raised its join event (finished, already cancelled, or abandoned). A graft that has already finished keeps its queued join and its reason. Ids are taken one at a time: in a call that names a running graft and a bad id, the graft is cancelled and the bad id is reported. A malformed item is shown back as a short, cut-off repr, never in full, so model-written text cannot put a long or multi-line string into the tool result.

A cancel is the original's own act, not a hand-back, and it is never routed to a new clone. A cancelled graft is left out of the "still running" lists from the moment the cancel is accepted. If the user's call is cancelled while a graft is being stopped, the call is answered at once, and the machine still completes the stop, queues the join and stores the tool result. After the run has ended the join event is raised whatever the store does; a store error while it is recorded (closing the graft's timeline, writing the reason) is shown to the user at once as a harness error line and does not change the tool result, the turn or shutdown; the reason is written again when the join is applied. If the write of the cancel call's own result row fails, the user is told that this write failed, and that a graft was stopped only if the call stopped one; the run ends with that error, and the row then written holds the real result, which the machine kept. A clone call that came in the same response is then not run (its tool call is answered as not executed when the run's open calls are closed).

**A running graft cannot be steered.** Clones are single-use and timelines never message each other. A follow-up on work that is still out waits for the join, or for a cancel, and then means a new clone.

**What this costs the "no telephone" claim.** A focus graft joins the conversation the user actually had. A background graft joins what it wrote with nobody reading: still its own rows, by pointer, with no model call and nothing rewritten, but the user saw none of it, and what the user hears is the source's account of those rows.

### Single use

Clones are single-use. A clone joins once and never runs again. Agents never message each other: the only cross-timeline events are the **seed** going down and the **join event** going up. Follow-up work always means a new clone, seeded from the source's timeline (which now holds whatever it joined).

## User Experience

- **Clones are invisible to the user.** There is one agent and one conversation; the user never sees the seams.
- **A clone never says "I can't do that."** Anything outside its part it leaves to its source: it merges, and the source handles it.
- **A focus graft holds the conversation for one turn.** It answers the message it was made for (or asks the user what it needs), and its turn ends in its join, by its merge call or implicitly; the source then runs once, and goes on with what is still to do or ends without saying anything. A user's answer to a focus graft's question reaches the source, which forks again for it (the new branch is pointed at what it needs). There is no separate record of a result. A host that shows a clone's progress shows its replies as they are written (they are rows in the store), and reads a join as "this clone's turn has ended", not "its result is ready".
- **Background work is reported by the agent, not by the clone.** While background grafts run the user keeps talking to the same agent; when they finish, the agent says what it did, in its own words and in the first person (it did the work, in a branch of itself).
- **A clone does only its own part of what it starts with.** The messages a clone is seeded with may ask for several things. It does the part its source's reason gives it (or, without one, the part its skills cover). The other parts belong to other clones or to the source: it does not attempt them, apologise for them or mention them, and never hands them back.
- **Only the source splits a request.** A message the user sends after a focus graft's turn reaches the source, never the graft (a message that came while the graft's turn ran comes back with its join): the source answers it, or forks for it. In "make the header darker and email the draft to Bob", the source sends the email itself, then forks c8 for the header.
- **Honesty guard.** Invisibility is an implementation detail, like process scheduling, not a persona. Asked directly, the agent answers truthfully: "I'm the same assistant; I narrowed my tools for this task."

## Host Interface (A2A)

graft speaks to its host in the **Agent2Agent protocol (A2A), version 1.0.1** (tag `v1.0.1` of github.com/a2aproject/A2A, released 2026-05-28; the JSON Schema bundle `https://a2a-protocol.org/v1.0.1/spec/a2a.json` is vendored as `tests/a2a/a2a-v1.0.1.json` with its sha256 in `tests/a2a/SOURCE.md`). Every object graft takes from or gives to its host is an A2A object in its ProtoJSON form (camelCase fields, enum names such as `TASK_STATE_WORKING` and `ROLE_AGENT`), so a JSON-RPC, HTTP+JSON or stdio codec is a thin layer over it. The host never sees a branch: the user hears one "I", and branches, forks, merges, rows, seeds and machines never appear on the wire.

### Surface

The interface is the A2A operations, in-process. This version has no transport of its own (no server, no CLI `serve`): the Python class `GraftAgent` exposes each operation as one method that takes and returns the A2A JSON objects (dataclasses that round-trip that JSON exactly), and adds nothing.

| A2A operation (JSON-RPC method) | Python | Result |
|---|---|---|
| `SendMessage` | `await agent.send(SendMessageRequest)` | `SendMessageResponse` holding a `task` (never a bare `message`) |
| `SendStreamingMessage` | `agent.stream(SendMessageRequest)` (async iterator) | `StreamResponse`s: the `task`, then `statusUpdate`s until the task is terminal |
| `GetTask` | `agent.get_task(GetTaskRequest)` | `Task` |
| `ListTasks` | `agent.list_tasks(ListTasksRequest)` | `ListTasksResponse` |
| `CancelTask` | `await agent.cancel_task(CancelTaskRequest)` | `Task` |
| `SubscribeToTask` | `agent.subscribe(SubscribeToTaskRequest)` (async iterator) | as `SendStreamingMessage`, from the task's current state |
| the Agent Card (`/.well-known/agent-card.json`) | `agent.card()` | `AgentCard` |
| `GetExtendedAgentCard` | not offered | `UnsupportedOperationError` (`capabilities.extendedAgentCard` is false) |
| push notification configs | not offered | `PushNotificationNotSupportedError` (`capabilities.pushNotifications` is false) |

`await agent.close()` shuts the agent down (see Shutdown). Errors are the A2A errors with their JSON-RPC codes: `TaskNotFoundError` (-32001), `TaskNotCancelableError` (-32002), `PushNotificationNotSupportedError` (-32003), `UnsupportedOperationError` (-32004), `ContentTypeNotSupportedError` (-32005), and `-32602 Invalid params` for a request that is not a valid object. A request is untrusted input: it is validated whole before anything is done (fields and types as the schema and the proto's `REQUIRED` field behaviours say; camelCase names only; enum names only; a user message with `role` `ROLE_USER`, a non-empty `messageId` and at least one part, every part a `text` part, since graft takes text only; ids and texts bounded in length, a message's text at most `MAX_TEXT_CHARS`), and a request that fails is refused with no task made and no event written. An unknown field is ignored (A2A §5.7). The Agent Card names the agent, its version, `capabilities.streaming: true`, text in and out, one `supportedInterfaces` entry given by the host (default: the in-process interface, `urn:graft:in-process`, binding `GRAFT-INPROC`, protocol version `1.0`), and one `AgentSkill` per capability skill in the catalog (not the built-in `fork`, `merge`, `detached`): the skills main can fork a branch to hold.

### Tools

The host gives graft its capability tools as a list, `GraftAgent(..., tools=[Tool(...)])`, in the shape of an MCP tool definition (Model Context Protocol, `Tool`): `name`, optional `title` and `description`, `inputSchema` (a JSON Schema object), optional `outputSchema` and `annotations`, plus the host's own callable, which is not part of the definition. There is no `World`: a tool is a definition and a function. graft calls the function with the call's arguments object (one `dict`); it may return its result or an awaitable of it. The result follows MCP's `CallToolResult`: `content` (a list of content blocks; a returned `str` is one text block), optional `structuredContent`, and `isError`; a function that raises gives `isError: true` with the error named (it ran: it may have acted), and anything else it returns is a result marked run with an error. What the model reads of a result is its text blocks, or, with none, its `structuredContent` as JSON. Cancellation is unchanged (State machine: a host tool call is the activity of a state): a call cut short where it waits is cancelled there and recorded as run with an error.

A skill names its tools by name; the skill catalog and the host's tools are matched by name when the agent is made (a skill that names a tool the host did not give is refused then, and two tools with one name are refused). graft's own tools (`load_skill`, `fork`, `merge`, `stop`) are graft's, in the same shape, and a host tool may not take one of their names. Each provider adapter encodes a tool for its wire (OpenAI Responses `parameters`, OpenAI Chat `function.parameters`, Anthropic `input_schema`). The simulated skills' tools (website, slides, calendar and the rest) are a fake tool list beside the fake model (`graft/fake.py`), used by tests, the simulator and the experiments; they are not part of the interface.

### Context and tasks

One `GraftAgent` holds one conversation: its `contextId`. A message whose `contextId` names another context is refused (`-32602`), and one without a `contextId` belongs to this one.

**A task is a user's request, not a branch.** Each message the host sends without a `taskId` opens a new task: that request and all the work it sets off, in every branch. A message with a `taskId` continues that task (A2A §3.4.3), while it is not terminal: its request is one more request of the task. An unknown `taskId` is `TaskNotFoundError`; the `taskId` of a terminal task is `UnsupportedOperationError`. Several tasks may be open at once in the context: their requests are answered in arrival order, as user messages always are.

A task's **work** is: each of its requests until it is answered (from the moment the session accepts it, through the original's inbox, the run that answers it and any focus graft that holds the conversation for it, to the rest at which its answer is given); every background graft made for it until its join has been applied or given up; and every run that is for it, until it ends. **A run is for a set of requests**: the request its turn answers (or the request a focus graft handed back, which a wake then answers), and the requests of the background grafts whose merges it reports (the original's `woken_for`). A run's tasks are those requests' tasks. A background graft is made for every live request of the run that forks it, so a branch forked in a wake belongs to every task whose merge caused that wake and keeps each of them open; it is stopped when **any** of its requests is withdrawn (a cancel of any of those tasks stops it). One liveness rule holds for runs: a run that answers a request ends when that request is withdrawn; a run that answers none (a wake) ends when every request it reports is withdrawn; a clone call is refused only when the run has no live request left (or is not for a request at all and the rules above refuse it). A run for no request (a turn its caller drives: tests, replay) makes grafts that belong to no task.

States, as A2A names them:

| State | When |
|---|---|
| `TASK_STATE_SUBMITTED` | the task is made (its first message), or a follow-up message reaches it while it is `INPUT_REQUIRED` |
| `TASK_STATE_WORKING` | a run for it begins (a turn on one of its requests, or a run that reports one of its grafts' merges), or it says something |
| `TASK_STATE_INPUT_REQUIRED` | **the turn ended**, and work of the task is still out (background grafts made for it run, or their joins wait) |
| `TASK_STATE_COMPLETED` | the turn ended and none of its work is out: every graft made for it has merged and main's run after the last such merge has ended |
| `TASK_STATE_FAILED` | as `COMPLETED`, but a request of the task failed (a step it set off failed, and the error went to that request) |
| `TASK_STATE_CANCELED` | `CancelTask` accepted |

**Turn end** is the point the conversation comes back to rest at main: main's run (and the joins and the wake that follow it) is over and no message waits. That is the point `SendMessage` returns, so the host gets main's reply when main's turn ends, not when every background branch has merged. A task whose work is still out is then `INPUT_REQUIRED`: the user may answer (a follow-up with its `taskId`) or speak of something else (a message without one, a new task), and the task goes back to `WORKING` when a run for it begins (a follow-up, or a merge of one of its branches) and back to `INPUT_REQUIRED` at the next turn end, until none of its work is out. A task becomes terminal only at a rest of the original: **at every rest of the original, every open task none of whose requests is unanswered is decided**: owed (a graft made for it whose join is neither applied nor given up) → `INPUT_REQUIRED`; else `COMPLETED`, or `FAILED` if an error went to it. So the decision does not depend on any record the session built up event by event: a follow-up the session has accepted but the original has not answered yet keeps its task open, however the turns around it end. A focus graft that comes to rest without a turn (a fault before its run began) ends a turn for the tasks it holds as `INPUT_REQUIRED` and is not a terminal point: main decides what is out once the conversation is back. A join whose commit failed is retried at the next commit point (State machine); a task whose last work is such a join stays `INPUT_REQUIRED` until then, and `CancelTask` ends it.

**What graft cannot tell.** Whether a reply asks the user something is model text, not a fact graft can observe, so `INPUT_REQUIRED` is structural (work is out), never "the agent asked a question". A turn that ends with nothing out completes its task even if the reply was a question; the user's answer is then a new task in the same context (A2A's context continuity), and main reads it with the conversation as always. A follow-up continues the same task only while that task is open.

**Text.** What main or a focus graft says to the user is an agent `Message` (`ROLE_AGENT`, one text part, a fresh `messageId`, the task's `taskId` and the `contextId`), carried by a `statusUpdate` of each open task the run is for (so a turn that reports another task's merges tells its text on both), with state `TASK_STATE_WORKING`, and kept in that task's `history`. The status update at a turn end, or a terminal one, carries the task's last agent message after its last user message, if any (the same message, so `history` holds it once). Text a run for no task says (a turn its caller drives) is a context-level `Message` in the event log, outside any task. Text said for a task that is already terminal is not delivered: it stays a row of the timeline. A background graft's text is never said (see Parallel grafts).

**Errors.** Every failure is an event. An error that went to a user's request is told on its task at the rest that answers the request (the request's answer is the error), and makes the task `FAILED` once none of its work is out; until then the task goes `INPUT_REQUIRED` with the error as its status message. A join that is given up (abandoned) is such an error of the tasks its graft was made for. Every other failure (a wake run that failed, a join commit that failed, a graft that could not be stopped, a write the scribe could not make, a fault no caller was given) is a **harness error**: an agent `Message` whose text is the harness error line and whose `metadata` is `{"graft": {"error": true}}`. Every harness error goes to the session machine (`report`), whose step expands it, then and there, into a `statusUpdate` of each task it holds open, keeping that task's state (so every open task's stream shows it), or, with none open, a context-level `Message`, in order with its own decisions; the writer only writes what was decided. Nothing is ever told on a task after its terminal state. `SendMessage`, `SendStreamingMessage` and `SubscribeToTask` raise a harness error (`HarnessError`, with that line) once they have delivered an error event of their task: a blocking send raises instead of returning (the task stays readable by `GetTask`), and a stream yields the event and then raises. Fail closed: nothing that failed is only in the store.

### Cancel

`CancelTask` is **Stop: the user withdraws the request.** It is the session machine's decision: a task that is open is made `CANCELED` at once in the session, the withdrawal of each of its requests is sent to the original's machine **before** the `CANCELED` event is written, and every request of the task is withdrawn there by the path a withdrawn request has always taken (see State machine): a waiting message is dropped; a run answering it ends at its next step and its row is marked withdrawn; the background grafts made for it stop at their next step and merge `cancelled`, and their merges wake nothing; and **a focus graft holding the conversation for it merges too, `cancelled`** (one that never ran merges at once), so the conversation comes back to main and the next message goes to main. Every branch turn ends in a merge, with no exception for a withdrawal. Nothing a run did outside the conversation is undone; the merge results say what each stopped branch had run. A cancel of a terminal task is `TaskNotCancelableError`; of an unknown task, `TaskNotFoundError`. `CancelTask` returns the task once its `CANCELED` status is in the event log. By then the withdrawal is queued on the original's machine ahead of any question a run asks after it, so no model call, tool call or text starts for the task once the original has taken it (a run asks before every step; State machine), and nothing is told on the task after `CANCELED` (the session drops a text for a task it no longer holds open). Dropping a stream or a blocking call (the host's own cancel of `send`) is not a cancel: the task goes on (A2A §3.5.2).

### Delivery: the event log

Everything graft tells its host is an **event**, appended to a durable, ordered log per context (the store's `a2a_events` table: a sequence number and one A2A `StreamResponse` JSON object per row): `{"task": ...}` when a task is made, `{"statusUpdate": ...}` for every change of a task's state and every message on it, and `{"message": ...}` for a context-level message. **Only the session machine appends to the log**, as the activity of its `writing` state, so events are written in the order the session decided them, and the log is the confirmed record: `GetTask`, `ListTasks` and every stream fold it (a task's `task` row, then each `statusUpdate`, whose message joins its `history` once). A task's terminal state is decided once, by a session step, and written once.

Every consumer reads the log from its own **cursor** and waits for more by a request to the session (`events_wait`: a cursor and a reply future carried in the event), which the session answers when its `writing` has written past that cursor, or fails with the write's error. Any number of consumers may wait at once; none holds a queue, lock or future of its own. `SendMessage` returns once its task's row is written (with `configuration.returnImmediately`) or once the task reaches `INPUT_REQUIRED` or a terminal state after its own message; `SendStreamingMessage` and `SubscribeToTask` yield the task's events until it is terminal (A2A §3.1.2: a stream stays open through `INPUT_REQUIRED`).

### What changes in the machines

**The session machine owns the tasks and the log.** Its data: every task it was given (its request ids and, per request, whether it is waiting to be delivered, delivered or answered; its state; whether an error went to it), the requests each background graft was made for (until its join reaches the original), the events decided and not yet written (`pending`, each already given its log position when it is decided), the sends to make now (`outbox`) and those to make once the events before them are written (`after_write`, each with the position it waits for), the position written, the consumers waiting, and whether it is closing. **A session step changes its data only at its end, all at once** (each effect computes the new values, then assigns them), so a step that raises changes nothing, and its fault (Internal faults) loses only its own event. Its events:

- `submit` (from the host: a new task, or a follow-up of an open one, with the request and a reply): the reply says `accepted`, or `not_found`, `terminal` or `closing`. Accepted: the task is made, or the follow-up added (`SUBMITTED` if it was `INPUT_REQUIRED`), its event goes to `pending`, and the user message to `after_write`: the original gets it once the task's row is written.
- `answering` (a timeline wrote the row of a request and its run begins) and `graft_received` (a graft's join reached the original): the tasks concerned go `WORKING` (a status only; no decision depends on it).
- `said` (a run said a text, with the requests the run is for: its machine passes them to the run): a `WORKING` status with the message for each open task among them; a context-level message when the run is for none; nothing when all are terminal.
- `grafts_made` (now with each background graft's requests).
- `rested` (a timeline that holds the conversation came to rest: the requests it answered, each with the error it was answered with, if any, and, from the original, the tasks it still owes): the requests are answered (an error is told on its task). From the original, every open task none of whose requests is unanswered is decided as above (Context and tasks); the `call_done` of every request of a task that became terminal goes to `after_write`. From a focus graft (which owes nothing it can know of) every task with a request it answered goes `INPUT_REQUIRED`.
- `report` (a harness error, from a timeline, the scribe, or the session's own fault handling; an abandoned join's carries the tasks its graft was made for, which are marked failed): expanded as above, into `pending`.
- `resync` (a timeline's record re-stated after a fault): carries, besides the record, its background grafts' requests, and, from the original, the requests it answered whose calls are not done and the tasks it owes; when it says the original is at rest, the session decides the open tasks as at a `rested`, so a `rested` lost with a failed step is made up for.
- `cancel_task` (a task and a reply): an open task becomes `CANCELED` (into `pending`); its user messages not yet delivered leave `after_write` and are never sent; the withdrawal of each request the original was given goes to `outbox` (sent before the write) and their `call_done` to `after_write`; the reply says `accepted`, else `not_found`, `terminal` or `closing`.
- `events_wait` (a cursor and a reply): answered at once if the log is past the cursor, else kept; a kept wait whose reply is done (its consumer went away) is dropped at the next step that reads the waits. In `closed` it is answered at once (the log is final), and so is any later one.
- `shutdown` (close): the session is closing (data); see Shutdown.

The session's graph is one composite `live` that holds `ready`, `sending` (ticks once on entry; a choice sends the head of `outbox`, which leaves the outbox in the same effect, after its send is made, so a step that raises sends nothing and keeps it), `writing` (activity: appends `pending` in one SQL transaction, each event at the position it was given, so a batch written twice is written once; outcome `written` with the position) and a choice `flush` that every step ends in: `outbox` first, then `pending`, then, while closing, the shutdown steps (each graft's shutdown and then the original's are `outbox` items; `flush` goes to `stopping` once the original has closed, the open tasks are decided `FAILED` and written, and `pending` and `outbox` are empty), else `ready`. While `sending` or `writing`, other events only change data (internal transitions on `live`), and the choice after each send or write picks up what they added. `written` reconciles `pending` against the position written (an event at or before it leaves `pending`), answers every consumer whose cursor it passed, and moves the `after_write` sends whose position is written into `outbox`. A write that fails leaves `pending` as it was: every consumer waiting gets the error (`HarnessError`), and the batch is written again at the next `flush`, which the next event of the session starts (a write is never given up while the session lives; at shutdown a batch that still cannot be written is `close()`'s error). A fault of the session while `writing` waits for the activity's outcome (the fault is deferred in `writing`), and recovery reconciles `pending` against the store's position before it writes again.

**The timelines.** A `Request` carries its task, and its answer is recorded on it by the machine that answers it (a marker no caller reads: the answer travels in `rested`); `request_written` sends `answering`; `come_to_rest` sends `rested` with the requests it answered (and their errors) and, from the original, the tasks it owes; `_report` goes to the session, not the scribe; `grafts_made` and the re-stated record carry each graft's requests; a run is told the requests it is for (`run_busy(requests=...)`), and a background graft is made for the live ones (its `made_for` is a tuple, and it stops when any is withdrawn); the `call_done` of a request now comes from the session when its task is terminal, so a request stays withdrawable (cancelable) after the turn that answered it, until then. **A focus graft whose request is withdrawn merges `cancelled`**: from `withdrawing` (a run cut short, or a start on a withdrawn request) it goes to `handing_back` with the join reason `cancelled`, and at rest a withdrawal of the request it holds sends it there too; its source applies the join, and the request it hands back is withdrawn, so no wake runs (`after` → `withdrawing` → rest). **The scribe** keeps the store copies of states, the trace and the withdrawal marks; a write it cannot make is a `report` to the session. The session's settle states, `call_began`/`call_done` from callers and the errors kept for `settle` are gone.

### Shutdown

`close()` is the session's `shutdown`, kept as data in `live` (closing): nothing is woken from then on (the original is told first, an `outbox` item), each running graft is shut down (one `outbox` item each), and once their joins have reached the original, the original is shut down (an `outbox` item). A user message not yet delivered is not delivered (its task fails with the rest). When the original has closed, every task still open is `FAILED` ("the agent was closed before this request finished"), into `pending`, and `flush` goes to `stopping` only once that is written and `outbox` is empty, so no event decided before the close is lost. In `closing` and after, `submit` and `cancel_task` are answered `closing` (the host reports `UnsupportedOperationError`).

### Conformance

`tests/conformance/*.json` are language-neutral fixtures: each is a list of JSON-RPC 2.0 requests (`SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`, card) with the model replies the fake provider is scripted with, and the responses and stream events expected, ids normalised. A rebuild in another language, or a transport codec, replays the same files. Every object the interface emits in the test suite is validated against the vendored schema and against the proto's `REQUIRED` fields, camelCase names and enum names.

## Isolation Rules

1. A clone sees only its seed pointers, its source's clone turn (with its own fork result) and its linked skills. No implicit history: the seed is the text messages the source points at (or the decisions client's pick of them), never the source's other tool calls, tool results or loaded skills.
2. Only the text rows of the clone's working view and its merge call join back (for a focus graft, its user-visible conversation and the call that ended its turn); other tool calls, tool results and thinking stay in the clone's frozen timeline.
3. Information crosses timelines only through the `fork` call (down: the seed and the clone turn, with the source's `reason`) and the default join (up: the text rows and the merge call, with the clone's `reason`). Neither `reason` is read by the harness; each is model-written text the other side reads as an assistant message. A cancel carries no content: it stops a graft and forces its join. Neither does a focus graft's withdrawal mark on its source's view: it names a row the conversation already holds or gets back by the join.
4. **A timeline reads only its own context** (a host tool that waits on another graft's tool goes through the host's state, not graft's context: see Shared resources). No timeline has a tool that queries the store: each sees exactly the rows its context points at, rendered by the harness. A clone never reads its source or its siblings, including siblings running at the same time, and a source reaches a clone's rows only through that clone's join. A seed may point only at rows the source itself holds in its context, so a clone cannot be seeded with a running sibling's work or with tool output that never joined; the harness refuses any other row id. This is enforced in the harness (seed resolution and rendering), not by prompt; there is no SQLite authorizer or per-agent view.
5. The only writes are new turns and appended pointers from a committed clone or join (a clone's fork result; a join's close-out, implicit merge call and merge result), and withdrawal marks (which carry no content: they say a row was withdrawn, in the views of the conversation it was asked in).
6. **Least privilege:** a clone holds only its linked skills' tools.
7. **Joined rows keep their role and kind.** Clone content is never rewritten or promoted into a different role; the only new rows a join creates are the merge result in the source (a tool result, the harness's) and, for an implicit merge, the harness's merge call and its result in the clone's own timeline. A cancelled graft's merge result names the capability tools the graft executed and whether each returned an error, never their input or output. Tool output is never joined by default. A focus graft's merge call carries its optional `reason`, which the user did not see: like a background graft's text, it is model-written text that may restate tool output, and it enters the source's context in the assistant role, inside a tool call's arguments.

> **Isolation by default, permeability on demand.**

## Testing

Grafts give natural evaluation boundaries:

- **Skill evals** run as `skill + seed rows + tools`. Every clone's seed is a recorded pointer set, so any run is exactly replayable, and a skill's eval corpus is a set of seeds.
- **Gathering evals:** given this timeline, did the source pick the right skills, and did the decisions client seed the right rows?
- **Join evals:** given this frozen clone timeline and trigger, did the source remember the right things?
- **Integration:** routing, scope detection (did the clone join when it should have), and end-to-end conversations.

Honest limit: clones inherit system instructions and the model, so changing those changes every clone. What grafts guarantee is that adding a skill does not change *other skills'* execution environments.

## Prior Art

| Existing | What it does | What differs here |
|---|---|---|
| OpenAI Agents SDK handoffs | Control passes to another agent that talks to the user; history filtered by `input_filter`. | Targets are separate agents, not clones; history passes by default; nothing joins back. |
| Context-Folding (Sun et al., 2025) | `fork`/`return` inside one agent's reasoning. | The branch returns a self-written summary (telephone); no user takeover. |
| Claude Code / Agent SDK subagents | Fresh context, task, returned summary. | Worker reports on itself; never talks to the user. |
| MemGPT / Letta | Paged memory tiers. | Memory tiers, not execution contexts. |
| Conversation branching (edit-branches, Loom) | Split timelines. | No join. |

What appears new as a whole: single-use clones that take over the user conversation, plus a **deterministic, pointer-based join** of the conversation itself, in which the worker never summarizes its own work.

## Future Ideas

- **`absorb(clone)`** (shelved): an on-demand recall where the source pulls detail the default join left out (a tool result, a pre-compaction turn) from a frozen descendant, via a read-only SQL transaction with validated commit. Dropped from v1 because no run needed it; add it back only if an experiment shows the source needs detail it cannot get otherwise.
- **Steering a running graft:** a way to pass a follow-up to work that is still out. (Cancelling one is in v1: see [Parallel grafts](#parallel-grafts).)
- **Ownership of external state:** a locking or ownership model for concurrent background grafts, replacing the rule that the source hands out non-colliding work.
- **Other seeder models:** v1 uses Jev. Alternatives (other decision APIs, a fine-tuned local model such as Needle 3) are worth revisiting once real-trace replays provide varied training and evaluation data. Needle 3 zero-shot did not qualify: its confidence did not separate needed rows from the rest.

## Non-goals

- Making specialized agents more capable than a single frontier model.
- Agent-to-agent messaging or negotiation.
- Clones that clone (see [Depth](#depth)).
- A new model or training method; this is a context-management and orchestration layer.

## Open Questions

1. **API verification.** Can spliced `thinking` blocks keep valid signatures? Do historical `tool_use` blocks require those tools to be declared on the timeline that reads them (a branch reads its source's `fork` call, and the source reads a branch's `merge` call, though neither holds that tool)? If either fails, joins drop thinking blocks or declare the tools disabled. A view may start with an assistant turn (a branch pointed at no messages): the OpenAI chat API takes that; whether every provider does is not verified here, and a provider that wants a user turn first is its adapter's to serve, never by a user-role row in the store.
2. **Join size** (implemented as a backstop). When the harness knows the model window (`window_tokens`), a join must leave the source's working view under 85% of it (the estimate is characters ÷ 4, and the reply needs room). The check runs at join time, not after compaction: compaction's own request carries the whole prefix, so it cannot rescue a view that is already over the window. The first of these that fits is committed: (0) every remembered row; (1) the clone's last assistant reply; (2) none of them. Every tier keeps the merge call, its merge result and the trigger, so the source's view stays paired and continuable (a merge call whose `reason` alone is over the window is still committed, by the last tier). The merge result says which rows were left out. They stay in the clone's frozen timeline, reachable by pointer. The window defaults per model (`providers.CONTEXT_WINDOWS`, by model-id prefix); `GRAFT_WINDOW_TOKENS` or bench `--window-tokens` overrides it (0 = off), and models with no known window are not checked.

## Validation Experiments

The baseline is **subagents**, not a single shared agent.

1. **Isolation (done, MVP):** the same skill as a clone vs inside a shared context with conflicting skills loaded. On gpt-6-luna both arms scored 20/20 with zero leakage; clones used about 3x fewer input tokens. Isolation alone does not distinguish the architecture on frontier models.
2. **Cost and caching vs subagents (in progress):** subagents diverge from the parent's cache and pay output tokens for the handoff prompt and the summary, plus prefill of each. Grafts replace both with pointer selection. Measured per role: uncached/cached input, cache writes, output.
3. **Fact loss vs selection recall (planned):** subagents lose facts by paraphrase (summary caps, compaction, nested delegation); grafts lose them only by selection (the source failing to seed or join a relevant row). Compare on tasks with many specific facts, a sweep of summary caps, and delegation depth 1-3.
4. **Replay on real traces (pilot run, `experiments/replay/`):** take existing Claude Code / Codex transcripts with subagents. At each point where a subagent finished, emulate a join: replace the summary tool_result with the default join over the subagent's actual transcript, then compare how the parent continues (next action, answers to probe questions about the subagent's work, tokens) against the recorded trace. This tests the join on real work without building a full runtime first.

   Also force the handoff: at the point where the parent invoked the subagent, cut the parent and make a `fork` call instead of letting it write a handoff prompt, then run a fresh clone from that seed and join it back. Compare that full counterfactual branch (seed → clone run → join → parent continuation) against the recorded branch (handoff prompt → subagent → summary → parent continuation). Clone runs need the environment as it was at that point, so start with read-only subagents (code search and research) replayed against the repository checked out at the trace's commit; subagents with side effects come later, if at all.

   Pilot results are in the README under "Results so far": with both arms on the same delegate model, neither the clone nor the subagent was clearly better, and the delegate model dominated the outcome.
5. **Parallel grafts vs sequential clone-join (mechanics only, `experiments/parallel.py`):** the same multi-part request as one clone call with background grafts, and as one focus clone per part. Offline, with a scripted provider, both arms pass the same checks on the simulated world (the two worlds are not compared with each other, and the arms are not the same script: one message per part against one message for all parts). In both arms a clone that ends its turn on a question while the checks are unmet gets one fixed user reply, at most three times per arm, so that a live clone asking for details is not scored as a harness failure; the number used is reported. Whether a real model routes parts to background grafts sensibly, whether quality holds against the sequential baseline, and the real wall-clock gain are not measured yet.

## Principle

Agent Grafts assumes **context boundaries are useful even when the model is capable of doing everything**, that **the agent which delegates decides what each branch sees**, and that **what comes back is the branch's own record, chosen by no one**.

> **One agent identity, single-use cloned timelines, everything queryable, a seed chosen by the source, and a lossless join.**
